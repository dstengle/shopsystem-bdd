# Example context: a notes CLI

This folder is a whole bounded context, small enough to read in ten minutes. It describes `notes`, a command-line
tool that keeps short notes. It is not the plugin, so you see the requirement language working on somebody else's
words.

It's written for the developer setting up a first repository. [Getting started](../../getting-started.md) copies
its files one by one. The docs test runs `spec check` and `features generate --check` on it, so what you read here
stays true.

## The whole idea in one line

Here is one line from the capability file, and the scenario the plugin generated from it:

```markdown
- [r2] If the person adds a note without a title, then the notes service shall refuse the request and name the title.
```

```gherkin
  @g2 @r2
  Scenario: A note added without a title is refused
    Given a note n1
    When the person adds the note n1 without a title
    Then the notes service refuses this request
    And the notes service names the title
```

You write the line. The plugin parses it, checks it, and writes the scenario. Nobody edits the scenario by hand:
when the line changes, it is generated again.

The line says nothing about a command, an option or an exit code. It says what the person asks of the notes service
(a request: add a note, without a title) and what the service answers (it refuses the request and names the title).
That `notes add` is the command and `--title` the option is the CLI adapter's business, written once in
`spec/adapters/cli.toml`. Put an HTTP service in front of the same notes and not one line changes.

The spec files and the program are written by hand; the feature file, and each operation's `requirements` in
`cli.toml`, are written by commands.

The folder holds three of a specification's four parts: the domain model, the vocabulary and the requirements. The
fourth, the decisions (`spec/decisions/`, each written by `work decision`), records the choices behind them; this
example has made none worth keeping yet. [Concepts](../../concepts.md#the-spec) has all four.

## `spec/index.md`: the context

```markdown
---
id: bounded-context/example.org/notes/notes-cli
title: notes
language: codified-2
imports: [request]
---

# notes

## Purpose

A command-line tool that keeps short notes: the person adds a note, lists them and removes one. It is not an editor
and not a sync service.

## Composition

| area | kind | capabilities |
|---|---|---|
| notes-cli | core | notes |
```

- **`language: codified-2`** says the files are written in the plugin's controlled language. Every capability file
  says it too.
- **`imports: [request]`** brings in the request pack: the words of a request and its response that every context
  needs, such as *request*, *service*, *refuse*, *name*, *return*, *keep* and *complete*. That's why the vocabulary
  doesn't define them. The pack is [`grammar/packs/request.md`](../../../grammar/packs/request.md).
- **Composition** lists the areas of the context, here one, and the capabilities of each.

## `spec/model/notes-cli.md`: the domain model

````markdown
---
id: model/example.org/notes/notes-cli/notes-cli
area: notes-cli
kind: core
imports: []
---

# notes

## Purpose

The notes the person keeps, the tags they are filed under, and the notes service that answers the person's requests.

```model
object note
  attributes: title (text); status: kept | removed
  lifecycle status: kept → removed
  relations: under → tag (many)

object tag

service notes
  operation add(title, tag)  outcomes: done → the note | refused: no title
  operation list()  outcomes: returned → every note
  operation remove(note)  outcomes: done

actor the person kind of agent
```
````

The model holds the structure and no rules: the objects, their attributes, the lifecycle of a note's status, the
relation of a note to its tags, and the notes service with its three operations. Each operation names its
parameters (`add(title, tag)`) and the kinds of outcome it has: done, returned, refused with a reason. The syntax is
in [The domain model](../../reference/domain-model.md).

## `spec/vocabulary/`: the words

```markdown
---
id: vocabulary/example.org/notes/notes-cli/notes-cli
area: notes-cli
---

# The words of notes-cli

## Terms

- **the notes service** (proper noun) → service notes. What answers the person's requests about notes.
- **note** (noun) → object note. One short text the person keeps, with a title.
- **tag** (noun) → object tag. A word the person files a note under.
- **title** (attribute) → attribute note.title. The one line that names a note.
- **status** (attribute) → attribute note.status. Whether a note is kept or removed.
- **kept** (adjective) → value note.status kept.
- **removed** (adjective) → value note.status removed.
- **add** (verb, action) → operation notes.add. Forms: adds, added. Frame: <actor> adds <note>.
- **list** (verb, action) → operation notes.list. Forms: lists, listed. Frame: <actor> lists the notes.
- **remove** (verb, action) → operation notes.remove. Forms: removes, removed. Frame: <actor> removes <note>.
```

```markdown
---
id: vocabulary/example.org/notes/notes-cli/shared
---

# Shared words

## Terms

- **the person** (proper noun) → actor the person. The human at the terminal.
```

Each entry names one element of the model after the arrow. A line can only use words that are here or in a pack.

- **A verb that names an operation** is how a line says a request: "the person adds a note" is a request of
  `notes.add`. Its parameters need no frame: a line says them after the object, "with a title and a tag", "without
  a title".
- **`Frame:`** is thin: the word order and the prepositions only. `<actor> adds <note>` means an actor adds, and what
  it adds is a note. The kinds come from the model.
- **The relation `under`** gives "a note under a tag" its meaning, with no word of its own.

## `spec/capabilities/notes.md`: what the service does

````markdown
---
id: capability/example.org/notes/notes-cli/notes
title: Notes
narrator: the person
group: service
area: notes-cli
specifies: service notes
language: codified-2
rests_on: []
retired: []
unbuilt: []
---

# Notes

## Purpose

Adding, listing and removing notes.

## Behaviour

### [g1] A note added with a title and a tag is kept
- [r1] When the person adds a note with a title and a tag, the notes service shall keep the note under the tag.

### [g2] A note added without a title is refused
- [r2] If the person adds a note without a title, then the notes service shall refuse the request and name the title.

### [g3] Listing the notes returns every note
- [r3] When the person lists the notes, the notes service shall return every note.

### [g4] Removing a note sets its status to removed
- [r4] When the person removes a note, the notes service shall set the status of the note to `removed`.

## Dropped
````

Four groups, each a different shape of line:

| group | form | read it as |
|---|---|---|
| g1 | event-driven: **When** ..., ... **shall** | the person makes a request with two parameters; the service keeps the note under the tag. |
| g2 | unwanted behaviour: **If** ..., **then** ... **shall** | a parameter is missing; the service refuses the request and says why. |
| g3 | event-driven, about **every** thing | "every note" is tested on two notes. |
| g4 | event-driven, with a definite | "a note" introduces the note; "the note" later means that same one. |

A few fields of the frontmatter matter from day one:

- **`id`** names the capability. Its groups and lines are `notes#g3`, `notes#r3` and so on.
- **`area:`** is the area of the model the lines are read in; **`specifies:`** names what the capability is about.
- **`unbuilt:`** lists the ids that have no code yet. Their scenarios run as expected failures. It's empty here.
- **`retired:`** is where an old id goes when a line changes. A line is never edited in place: it gets a new id.

## `spec/adapters/cli.toml`: how the CLI asks

```toml
# The CLI adapter's contract of the notes service: each operation of the domain model with the command that requests
# it and the option or argument of each parameter, checked both ways against notes.py's argparse by `spec check`.
adapter = "cli"
json = "--json"

[programs]
notes = "notes.py"

[outcomes]
done = { exit = 0 }
returned = { exit = 0, content = "stdout" }
refused = { exit = 1, errors = "stderr" }
broken = { exit = 1, errors = "stderr" }

[cli-only]
options = ["--root", "--json"]

[operations."notes.add"]
command = "notes add"
requirements = [
  "notes#r1: When the person adds a note with a title and a tag, the notes service shall keep the note under the tag.",
  "notes#r2: If the person adds a note without a title, then the notes service shall refuse the request and name the title.",
]
[operations."notes.add".parameters]
title = { option = "--title", example = "Buy milk" }
tag = { option = "--tag", repeat = true }

[operations."notes.list"]
command = "notes list"
requirements = [
  "notes#r3: When the person lists the notes, the notes service shall return every note.",
]

[operations."notes.remove"]
command = "notes remove"
requirements = [
  "notes#r4: When the person removes a note, the notes service shall set the status of the note to `removed`.",
]
[operations."notes.remove".parameters]
note = { positional = 1, example = "1" }
```

The adapter's contract maps each operation to the command that requests it and each parameter to its option or
argument, and says how each outcome shows: exit 0 for done and returned, exit 1 with the reasons on stderr for a
refusal. `spec check` reads `notes.py`'s argparse and checks the two both ways: every operation has a command, every
command and option is named (v_a1-v_a4).

Each operation's `requirements` are the lines that govern it, the lines whose trigger requests it, refusals
included: whoever changes `notes add` reads its business rules right there. They are generated: `spec annotate`
writes them, and `spec check` fails an operation that misses a governing line or keeps one that no longer governs
it (v_a5, v_a6). The format is in [Adapter contracts](../../reference/adapters.md).

## `features/notes.feature`: what the plugin generated

```gherkin
# generated from spec/capabilities/notes.md by features generate; do not edit
Feature: Notes
  Narrator: the person

  @g1 @r1
  Scenario: A note added with a title and a tag is kept
    Given a note n1
    And a tag t1
    When the person adds the note n1 with a title and the tag t1
    Then the note n1 is under the tag t1
    And the notes service keeps the note n1

  @g2 @r2
  Scenario: A note added without a title is refused
    Given a note n1
    When the person adds the note n1 without a title
    Then the notes service refuses this request
    And the notes service names the title

  @g3 @r3
  Scenario: Listing the notes returns every note
    Given a note n1
    And a note n2
    When the person lists the notes
    Then the notes service returns the note n1
    And the notes service returns the note n2

  @g4 @r4
  Scenario: Removing a note sets its status to removed
    Given a note n1
    When the person removes the note n1
    Then the notes service sets the status of the note n1 to `removed`
```

Things to notice:

- **One scenario a group**, tagged with the group and its line: `@g3 @r3`. A test failure points straight back to
  the line.
- **"every note" became two notes, n1 and n2.** A scenario can't test every note there is, so the generator
  brings in two and says the Then of each.
- **"this request"** is the request the When makes: the service refuses that one.
- **Names like n1 and t1** stand for the instances the line talks about. Your step handlers bind them to real
  notes and tags, and drive the program through its adapter.

Binding these steps to code with pytest-bdd is in [Getting started](../../getting-started.md).

## What a line means

`spec parse --form` prints what the plugin reads a line as. Here is the refusal line, g2:

```console
$ spec --root docs/examples/notes-cli parse --form "If the person adds a note without a title, then the notes service shall refuse the request and name the title."
shall [x1: agent the person (constant), x3: service the notes service (constant), x4: request "the request the trigger makes" (indexical), x5: parameter title (constant)]
  if [x2: note]
    request(e1, notes.add, subject: x1, object: x2)
    noparam(e1, title)
  response
    refuse(e2, subject: x3, object: x4)
    name(e3, subject: x3, object: x5)
```

Read it top to bottom. The square brackets are the things the line talks about: the person, the service, the
request and the parameter. **If** is what goes wrong: the person requests `notes.add` on a note with no title.
**Response** is what the notes service must do: refuse that same request (x4, the one the trigger makes) and name
the title (x5).

These lines parse in this context's grammar, not in the plugin's own: always pass `--root docs/examples/notes-cli`.

## A line that is refused, and its fix

A counter-example. This line is **refused**:

```console
$ spec --root docs/examples/notes-cli parse "When the person removes the note, the notes service shall set the status of the note to \`removed\`."
refused: "the note" has no antecedent: no earlier noun phrase, functional relation or declared indexical gives a note
  tree: ...
```

"The note" points back to a note, but nothing before it introduced one. Which note would the service remove? Say
where the note comes from, and the line parses. That's g4's line:

```markdown
- [r4] When the person removes a note, the notes service shall set the status of the note to `removed`.
```

There are more pairs like this in [Writing requirements](../../writing-requirements.md).

## What this context needed beyond the brief

The aim was the smallest context that passes every check. Three things were added for that, and nothing else:

- **The feature file.** Without it, `spec check` reports `v_s3  a group has no scenario` for each group.
  `features generate` writes it.
- **A line for every operation.** `spec check` reports `v_m7  an operation no line requests` for an operation of the
  model that no line asks for, and `v_m4` for a refusal reason no line states (`no title` is g2's).
- **`notes.py`.** The adapter's contract names a program, and `spec check` reads its argparse: a command or an
  option the contract names that the program lacks is `v_a3`, one the program has that the contract does not name
  is `v_a4`.

`spec check` asked for no decisions, records or backlog. A context can start with only a spec; the `.shop/` folder
comes when you start working with Claude.
