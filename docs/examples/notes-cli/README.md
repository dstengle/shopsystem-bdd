# Example context: a notes CLI

This folder is a whole bounded context, small enough to read in five minutes. It describes `notes`, an imaginary
command-line tool that keeps short notes in one file. It is not the plugin, so you see the requirement language
working on somebody else's words.

It's written for the developer setting up a first repository. [Getting started](../../getting-started.md) copies
its files one by one. The docs test runs `model check` and `features generate --check` on it, so what you read here
stays true.

## The whole idea in one line

Here is one line from the capability file, and the scenario the plugin generated from it:

```markdown
- [r2] If the person runs `notes add` without the `--title` option, then `notes` shall refuse the command and name `--title`.
```

```gherkin
  @g2 @r2
  Scenario: `notes add` refuses a note with no title
    When the person runs `notes add` without the `--title` option
    Then `notes` refuses `notes add`
    And `notes` names the `--title` option
```

You write the line. The plugin parses it, checks it, and writes the scenario. Nobody edits the scenario by hand:
when the line changes, it is generated again.

## `spec/index.md`: the context and its words

```markdown
---
id: bounded-context/example.org/notes/notes-cli
title: notes
language: codified-2
imports: [cli]
---

# notes

## Purpose

A command-line tool that keeps short notes in one file: `notes add` writes a note, `notes list` prints them and
`notes remove` deletes one. It is not an editor and not a sync service.

## Relations

| from | word | to | cardinality |
|---|---|---|---|
| note | under | tag | many |
| title | of | note | one |

## Glossary

- **the person** (proper noun): the human at the terminal. Kind of: agent.
- **`notes`** (proper noun): the notes tool. Kind of: tool.
- **note** (noun): one short text the person keeps, with a title.
- **title** (noun): the one line that names a note.
- **tag** (noun): a word the person files a note under.
- **file** (noun): the one file on disk where `notes` keeps every note.
- **add** (verb, action): a tool keeps a new thing. Frame: tool adds note.
- **delete** (verb, action): a tool removes a thing for good. Frame: tool deletes note.
```

What each part does:

- **`language: codified-2`** says the files are written in the plugin's controlled language. Every capability file
  says it too.
- **`imports: [cli]`** brings in the CLI pack: the words every command-line tool needs, such as *command*,
  *option*, *run*, *print*, *exit*, *refuse* and *name*. That's why the glossary doesn't define them.
  The pack is [`grammar/packs/cli.md`](../../../grammar/packs/cli.md).
- **The glossary** is the lexicon. A line can only use words that are here or in a pack. Each entry names its part
  of speech in brackets.
- **`Kind of:`** places a word under a pack's word. `notes` is a *tool*, so it can print, exit and refuse.
  *The person* is an *agent*, so they can run a command.
- **`Frame:`** says who does a verb to what. "tool adds note" means only a tool adds, and what it adds is a note.
  A line that breaks a frame is refused.
- **The relations** give prepositions a meaning. "a note under a tag" and "the title of every note" parse because
  of these two rows.

## `spec/capabilities/notes.md`: what the tool does

````markdown
---
id: capability/example.org/notes/notes-cli/notes
title: Notes
narrator: the person
group: service
language: codified-2
rests_on: []
retired: []
unbuilt: []
---

# Notes

## Purpose

Adding, listing and removing notes.

## Behaviour

### [g1] `notes add` adds a note under a tag
- [r1] When the person runs `notes add` with the `--title` option and the `--tag` option, `notes` shall add a note under a tag and exit successfully.

### [g2] `notes add` refuses a note with no title
- [r2] If the person runs `notes add` without the `--title` option, then `notes` shall refuse the command and name `--title`.

### [g3] `notes list` prints every note
- [r3] When the person runs `notes list`, `notes` shall print the title of every note.

```given
the file `notes.json` holds:
  [{"title": "Buy milk", "tags": ["home"]},
   {"title": "Call the bank", "tags": []}]
```

### [g4] `notes remove` deletes a note
- [r4] When the person runs `notes remove` on a note, `notes` shall delete the note.

## Dropped
````

Four groups, each a different shape of line:

| group | form | read it as |
|---|---|---|
| g1 | event-driven: **When** ..., ... **shall** | something happens; the tool answers. Two answers joined with *and*. |
| g2 | unwanted behaviour: **If** ..., **then** ... **shall** | something goes wrong; the tool refuses and says why. |
| g3 | event-driven, with a **given block** | the sample notes live in the group's `given` block, never in the line. |
| g4 | event-driven, with a definite | "a note" introduces the note; "the note" later means that same one. |

A few fields of the frontmatter matter from day one:

- **`id`** names the capability. Its groups and lines are `notes#g3`, `notes#r3` and so on.
- **`unbuilt:`** lists the ids that have no code yet. Their scenarios run as expected failures. It's empty here
  because this example has no code at all; in your repository, a batch fills it and empties it as work lands.
- **`retired:`** is where an old id goes when a line changes. A line is never edited in place: it gets a new id.

## `features/notes.feature`: what the plugin generated

```gherkin
# generated from spec/capabilities/notes.md by features generate; do not edit
Feature: Notes
  Narrator: the person

  @g1 @r1
  Scenario: `notes add` adds a note under a tag
    When the person runs `notes add` with the `--title` and `--tag` options
    Then the note n1 is under the tag t1
    And `notes` adds the note n1
    And `notes` exits successfully

  @g2 @r2
  Scenario: `notes add` refuses a note with no title
    When the person runs `notes add` without the `--title` option
    Then `notes` refuses `notes add`
    And `notes` names the `--title` option

  @g3 @r3
  Scenario: `notes list` prints every note
    Given the file `notes.json` holds:
      """
      [{"title": "Buy milk", "tags": ["home"]},
       {"title": "Call the bank", "tags": []}]
      """
    And a note n1
    And a note n2
    When the person runs `notes list`
    Then the note n1 has the title t1
    And `notes` prints the title t1
    And the note n2 has the title t2
    And `notes` prints the title t2

  @g4 @r4
  Scenario: `notes remove` deletes a note
    Given a note n1
    When the person runs `notes remove` on the note n1
    Then `notes` deletes the note n1
```

Things to notice:

- **One scenario a group**, tagged with the group and its line: `@g3 @r3`. A test failure points straight back to
  the line.
- **"every note" became two notes, n1 and n2.** A scenario can't test every note there is, so the generator
  brings in two and says the Then of each.
- **The given block became a docstring.** Your step handler reads it and writes `notes.json` before the command
  runs.
- **Names like n1 and t1** stand for the instances the line talks about. Your step handlers bind them to real
  notes and titles.

Binding these steps to code with pytest-bdd is in [Getting started](../../getting-started.md).

## What a line means

`model parse --form` prints what the plugin reads a line as. Here is the refusal line, g2:

```console
$ model --root docs/examples/notes-cli parse --form "If the person runs \`notes add\` without the \`--title\` option, then \`notes\` shall refuse the command and name \`--title\`."
shall [x1: agent the person (constant), x2: command `notes add` (parameter), x3: option `--title` (parameter), x4: tool `notes` (constant)]
  if
    run(e1, subject: x1, object: x2, without: x3)
  response
    refuse(e2, subject: x4, object: x2)
    name(e3, subject: x4, object: x3)
```

Read it top to bottom. The square brackets are the things the line talks about: the person, the command, the
option and the tool. **If** is what goes wrong: the person runs `notes add` without `--title`. **Response** is
what `notes` must do: refuse that same command (x2) and name that same option (x3).

These lines parse in this context's grammar, not in the plugin's own: always pass `--root docs/examples/notes-cli`.

## A line that is refused, and its fix

A counter-example. This line is **refused**:

```console
$ model --root docs/examples/notes-cli parse "When the person runs \`notes remove\`, \`notes\` shall delete the note."
refused: "the note" has no antecedent: no earlier noun phrase, functional relation or declared indexical gives a note
  tree: ...
```

"The note" points back to a note, but nothing before it introduced one. Which note would `notes` delete? Say where
the note comes from, and the line parses. That's g4's line:

```markdown
- [r4] When the person runs `notes remove` on a note, `notes` shall delete the note.
```

There are more pairs like this in [Writing requirements](../../writing-requirements.md).

## What this context needed beyond the brief

The aim was the smallest context that passes every check. Three things were added for that, and nothing else:

- **The feature file.** Without it, `model check` reports `v_s3  a group has no scenario` for each group.
  `features generate` writes it.
- **`file` in the glossary.** The words of a given line must be words of the context. Without the entry,
  `features generate` stops with ``the given line 'the file `notes.json` holds:' does not parse in the step
  grammar 4 at file (token 2)``.
- **`title` as a noun with a relation row**, not an `attribute of note`. An attribute is meant to have `Values:`,
  and a title can be anything, so `model lexicon --check` reports `v_t4  title  spec/index.md: the attribute gives
  no Values`. As a noun with the row `title | of | note | one`, "the title of every note" parses and the lexicon is
  clean.

`model check` asked for no decisions, records or backlog. A context can start with only a spec; the `.shop/` folder
comes when you start working with Claude.
