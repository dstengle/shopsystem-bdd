# Capability files paired with feature files

Date: 2026-09-29 (stage 1; adopted by the plugin in 0.8.0); requirement ids 2026-10-16 (0.19.0, design model v3); final layout, decision files and ids for references 2026-10-19 (0.21.0)
Scope: one context, on its own. Nothing here needs agreement with another
repo, a product level, or any tooling beyond markdown and Gherkin.

## What stage 1 is

Replace one design note with a set of capability files, and formulate one
feature file per capability. That's all. Relationships, requests, threads,
and the corpus come later, each when something asks for it.

What you get immediately: every behaviour sentence has a condition and an
observable response, so gaps show up while writing; and every sentence
maps to one scenario, so features stop drifting from the spec.

## Layout

```
spec/
  index.md              the context: purpose, constraints, composition, order of building, testing
  decisions/
    <nnnn>-<slug>.md    one file per decision
    index.md            generated by `scripts/model decisions`, never written by hand
  capabilities/
    identity.md         one file per capability
    write-path.md
    ...
features/
  identity.feature      one per capability, same name
  write-path.feature
  ...
.shop/                  how the context is changed and what was noticed
  work/  records/       initiatives and their parts; observations, measurements, review findings, archive
  scratch/              drafts, notes and maps of a session; git-ignored, never read as the model
```

The pairing is by name, hyphenated on both sides. The capability `identity` (`capabilities/identity.md`)
is formulated in `features/identity.feature`: the feature file is `features/<name>.feature`, always, and
no field of the capability names it. The feature says so in its header. Nothing else links them.
`scripts/model` reads this layout and no other; an earlier layout is printed as file problems, and
`scripts/migrate` relocates it with git.

## The capability file

```markdown
---
id: capability/missingmass.io/shopsystem/shop-kb/identity
title: Identity
narrator: a client of the contract
rests_on: [design-decision/primary-model]
retired: []
---

# Identity

## Purpose
One paragraph: what this is, and what it isn't.

## Behaviour
EARS lines with "shall", each with its id: `- [r1] **When** ..., the <system> shall ...`. This is the only section scenarios are formulated from.

## Implementation, may change
Mechanism. Non-binding. Nothing here gets a scenario.

## Not yet
Deferrals, each with the trigger that promotes it.
```

Every sentence in the file is one of four kinds, and the section it sits
in says which:

| kind | section | falsified by |
|---|---|---|
| decision | `spec/decisions/`, cited by `rests_on` | argument, or its `revisit_when` |
| requirement | Behaviour | a scenario |
| implementation | Implementation, may change | measurement |
| scope | Not yet | its trigger firing |

A sentence that is none of these — rationale, intent, a comparison to what
was rejected — is cut from the capability. If it matters, it goes in the
decision it explains.

## Writing the behaviour section

Every line is one EARS requirement with "shall" (design-decision/behaviour-lines-are-ears). `model check`
prints a line that is not (`v_e1` (a Behaviour line is not in one of EARS's patterns)) or has more than one "shall" or sentence (`v_e2` (a Behaviour line has more than one "shall" or more than one sentence)).

**The patterns.** In this order of clauses; the system is named in the line.

| pattern | form |
|---|---|
| ubiquitous | `The <system> shall <response>.` |
| event-driven | `When <trigger>, the <system> shall <response>.` |
| state-driven | `While <state>, the <system> shall <response>.` |
| unwanted behaviour | `If <condition>, then the <system> shall <response>.` |
| optional feature | `Where <feature>, the <system> shall <response>.` |
| complex | the clauses combined: `Where`, then `While`, then one `When` or `If ... then`, then the system and its response |

**The pattern follows what starts the behaviour.** A response to a command, an input or an event is
event-driven, the trigger in its `When`. A refusal or a fault is unwanted behaviour, the condition in
`If ... then`. Behaviour that lasts for a period is state-driven. Behaviour that depends on an option or
configuration is optional. Only what is true with no trigger at all is ubiquitous.

**One "shall", one response, one sentence.** A line with two responses is two lines. Conditions with the same
response join in one line: `If A or B, then ...`.

**An `If` line earns its place** only when it is the capability's purpose (a verifier that prints problems),
protects the person's files from loss or silent damage, or answers a failure that has been seen. Every other
failure is covered by one line per script or agent: `If <system> cannot do what it was asked, then <system>
shall exit with an error, say why, and change nothing.` A failure seen in practice earns its own line from that
evidence.

**Exits in words.** A line says a command exits successfully or exits with an error, never an exit code
(design-decision/exits-are-successful-or-errors). Where a command has several error codes, they are listed in
its Implementation section and checked by unit tests. A command that stops because it waits on the person (a
work-item awaiting a ruling) exits with an error.

**The response is observable by the narrator.** A value returned, a refusal and what it names, a file at a
path. If you can't write the response that way, the sentence is implementation and goes down a section.
A refusal names its reason; the words of a message, a status code, a field name and minor refusals are implementation.

**Tables.** A verifier's rules may be a table: a sentence that names the system and says "shall" leads it, and
each row has an id in its first cell, `| [r3] | ... |`, and counts as a line, judged by its lead sentence.
A list of properties (a canonical format) stays a list.

**Skeletons.** A capability not yet built is specified as a walking skeleton, a handful of lines, and grows
from what running it shows.

## Lines that leave nothing to infer

Five lessons from 0.22.0's blind formulation, where a formulator who sees only `spec/` had to ask. Each is a
kind of finding `checking-spec-consistency` reports; the first is also one a review reports.

1. **Behaviour reaches code only through a line.** A fix work-item that adds behaviour writes its line first,
   at the gate; a review grades code no line asks for Important. Supervision's code and scenarios said
   `work run` says why "in one line"; r10 asks only that it say why, so the formulator could not tell whether
   to keep the words.
2. **Lines that touch one thing say which wins, and a line names its reach.** Supervision r28 and r34 both
   catch a change under `.shop/work/` when a worker ends; r28 sent the work-item to `awaiting-ruling` and r34
   to `failed` until decision 0056 said both are `failed`. r22 names its reach, "every pytest command it
   starts, and every worker's", rather than leaving the reader to infer which runs.
3. **One scenario shows one line's response** (design-decision/a-scenario-names-one-requirement). A refusal or
   an exit belongs to the capability's general failure line, or to Implementation, never trailed onto another
   line's scenario; exits are in words (design-decision/exits-are-successful-or-errors). Work-queue's
   `@r2 @r7` scenario showed r7's exit after r2's response; it became two scenarios.
4. **Anything with states is written as a lifecycle:** a line for each way into and out of each state. `failed`
   came with its ways in (supervision r28, r34, r39, r41), what holds while in it (r37) and its way out
   (work-queue r8, `work retry`); the formulator still found no line for `work retry` on a work-item that is
   not `failed`.
5. **A word a line depends on is a glossary term or spelled out in the line.** `failed` entered the glossary
   with the lines that use it; "in one line" was neither, so no scenario could pin it.

## Requirement ids

Every Behaviour line has an id, `[r<n>]`, written first: `- [r3] **If** ...`. The id is the line's
name for good: scenarios, proposals and commits point at it, and it survives re-wording.

- A new line takes the id one above every id the capability has used or retired, wherever it sits in the
  section. Ids are never renumbered, so they need not be in order. A round given ids that other
  initiatives' drafts add numbers its added lines above those ids too, on the same capability.
- A changed line keeps its id. A line whose meaning is replaced by a different rule is a removal and an
  addition, not a change.
- A removed line's id goes into the frontmatter's `retired: [r<n>, ...]` and is never taken again.
- A requirement is named `capability/<context path>/<name>#r<n>`, `capability/<name>#r<n>` or `<name>#r<n>` inside its own context.

Ids are type-first, as in shopsystem-knowledge's IRIs: `<kind>/<context path>/<name>`. The context path is
the owner's domain, the product and the context name, such as `missingmass.io/shopsystem/shop-kb`. The
bounded context is `bounded-context/<context path>`, and it is `spec/index.md`'s `id`. A capability is
`capability/<context path>/<name>`, `<name>` being its file's name, and that is its `id`. A decision's `id` is
`design-decision/<context path>/<slug>`, `<slug>` being its file's name without the number. A frontmatter `id` is always written in full.

A reference may be shorter. `<kind>/<name>` names a node of the same context, as `design-decision/primary-model`.
A field that fixes the kind (`rests_on`, `supersedes`, `argues`, `under`, `depends_on`, a decision's `source`) and the capability part
of a `#r<n>` reference may write the bare `<name>`. Any other field, `about:` for one, needs `<kind>/<name>`.
A frontmatter field that names another file names it by its id, never by a path. `<context name>/<name>`, `decision/<name>` and `obs/<name>` are not ids; `model check` prints them as
unresolved.

A requirement `capability/<context path>/<name>#r<n>` is short for the part `capability/<context path>/<name>#behaviour/r<n>`.
The IRI of an id is shopsystem-knowledge's base followed by the id.

`spec/index.md` begins with the context's id:

```markdown
---
id: bounded-context/missingmass.io/shopsystem/shop-kb
title: shop-kb
---

# shop-kb
```

## Upstreams

A context that depends on others names each one in a `## Upstreams` section of `spec/index.md`, one bullet for
each: the upstream's bounded-context id, a colon, and the path of its published spec (its `spec/` directory; a
relative path is taken from the repository's root). An integrate round is given each upstream's id and the absolute
path of its spec, and gives the lines of a request into an upstream, in its glossary's terms, where a drafted line needs
what the upstream does not yet give.

```markdown
## Upstreams

- bounded-context/missingmass.io/shopsystem/billing: ../billing/spec
```

## Glossary

A bounded context's terms are its ubiquitous language: the one word its lines and scenarios use for each
thing the narrator names. Each term is a bullet of `spec/index.md`'s `## Glossary`, in exactly this form:

```markdown
## Glossary

- **revision**: the count of writes an item has had, 1 when it is created. Not: version.
- **journal**: the record of every write to the store, oldest first. Not: history, log.
- **schema**: the declaration of an item type's fields.
```

`- **<term>**: <one-sentence definition>. Not: <word>, <word>.` The definition is one sentence. The `Not:`
part is optional: it lists the words the context avoids for that thing, and it is split from the definition
at `. Not:` only, so a definition may contain a period. A bullet in that section of any other form is a file
problem.

A term is standing, like a Behaviour line, and is approved at the gate like one. Its id is
`term/<context path>/<term>`, the term lowercased with spaces as hyphens (`term/missingmass.io/shopsystem/shop-kb/revision`);
inside its context, `term/<term>`. A term contains letters, digits and hyphens once lowercased; any other character in it is a file problem. Renaming a term is removing one entry and adding another. A glossary
change is shown at the gate with the lines it comes with, and the spec commit names each term added,
changed and removed. In a repository that keeps `work/`, a term change rides with the capability-proposal
that needs it, which lists the term in `adds`, `changes` or `removes` (`adds: [term/revision]`).

`model check` reads every Behaviour line and every scenario not deprecated for the terms and the avoided words,
matched as whole words, whatever their case, with a plural "s" allowed. A scenario's mentions come from its title and its steps, not its Background, description, docstrings or tables: "restore" is no mention of "store".
It prints:

| rule | what it found |
|---|---|
| `v_t1` (a word the glossary avoids) | a line or a scenario uses a word its context's glossary lists after `Not:`; the row names the line or scenario, the word and the term |
| `v_t2` (a term has two entries) | two glossary entries have one term |
| `v_t3` (an avoided word is a term) | a word one term lists after `Not:` is another term of the context, or the term itself |

A word used for two things, or two words used for one thing that no `Not:` lists yet, or a word a line
depends on that is neither a term nor spelled out in the line, is a judgment of meaning, not a word match:
`checking-spec-consistency` finds it, on demand.

## The feature file

One feature per capability. One scenario per EARS line, or a scenario
outline where the line has a Where and several configurations matter.
A scenario names exactly one line (design-decision/a-scenario-names-one-requirement): it is tagged `@r<n>` with
the id of the line it formulates, on the scenario's tag line, and shows that line's response; the tag is
what binds them. Two lines that need the same setup or check get a scenario each, and the scenarios share
step definitions in code; that sharing never puts two lines in one scenario. A Then line says a command exits
successfully or exits with an error, never an exit code. The title is free; restating the line's condition is still a good title. A deprecated scenario
(tagged `@deprecated`) keeps the tag it had and formulates no line.

```gherkin
# formulated from spec/capabilities/identity.md
Feature: Identity
  Narrator: a client of the contract
```

EARS to Gherkin:

| EARS | Gherkin |
|---|---|
| Where / While (precondition) | Given |
| When (trigger) | When |
| If (unwanted) | When, with the invalid input |
| response | Then |
| ubiquitous | a property scenario, or Background |

## Worked pair

From kb's design note, the identity section. Four of its lines and their
scenarios; the other four follow the same shape.

### `spec/capabilities/identity.md` — Behaviour

- [r1] **When** `Create` is called with a title, kb mints `id` as
  `<type>/<slug>` and returns it with `revision` 1.
- [r2] **When** a minted id collides with an existing one, kb appends `-2`,
  `-3`, and so on, and returns the id it chose.
- [r3] **If** content on `Create`, `Write`, or `Append` has an identity
  key, `title` included, kb refuses the write with a violation naming the
  key.
- [r4] **Where** an item schema declares `title`, **when** an item is appended,
  kb mints its id from the title; otherwise from its position.

### `features/identity.feature`

```gherkin
# formulated from spec/capabilities/identity.md
Feature: Identity
  Narrator: a client of the contract

  @r1
  Scenario: Create with a title mints the id
    Given a store with a "decision" schema
    When Create is called with type "decision" and title "Use YAML"
    Then the response id is "decision/use-yaml"
    And the response revision is 1

  @r2
  Scenario: a colliding id gets a suffix
    Given a store with "decision/use-yaml"
    When Create is called with type "decision" and title "Use YAML"
    Then the response id is "decision/use-yaml-2"

  @r3
  Scenario: content with an identity key is refused
    Given a store with a "decision" schema
    When Write is called on "decision/use-yaml" with content that has "title"
    Then the write is refused
    And the violation names "title"

  @r4
  Scenario Outline: an item id is minted from title where the schema declares one
    Given a "process" schema whose step items <declare> a title
    When Append is called on "process/review#steps" with <item>
    Then the item id is <id>

    Examples:
      | declare | item                      | id      |
      | declare | title "Draft the note"    | draft-the-note |
      | omit    | no title                  | 0       |
```

## Decision files

A decision is one file, `spec/decisions/<nnnn>-<slug>.md`, `nnnn` one above the highest number in the
directory. The form is light (design-decision/light-decisions): frontmatter, then a title and a Decision
section. A decision that weighed no options is those and nothing more.

```markdown
---
id: design-decision/missingmass.io/shopsystem/shop-kb/delete-refuse-only
summary: "The only delete rule is refuse: a delete that would leave a reference dangling is refused."
date: 2026-09-23
status: accepted
supersedes: [design-decision/delete-cascade]
revisit_when: a request asks for cascade or detach
source: [initiative/delete-rules, observation/2026-09-20-dangling-refs]
by: "the person, 2026-09-23, on the kb design note"
---

# 0007. Delete refuses only

## Decision

The only delete rule is `refuse`.
```

- Frontmatter: `id`, `summary` (one sentence, required), `date`, `status`, and where they apply `supersedes`,
  `revisit_when` (only where someone will actually see the signal; otherwise the reasoning goes in the
  Decision), `revisit_signal`, `source` and `by`.
- `source` lists ids of nodes in the repository: records, an initiative, another decision. Everything else it
  came from, the person and a date, a delegation, a release or commit, a note outside the repository, is
  written in words in `by`, which `scripts/model` does not read.
- `## Context` and `## Alternatives` are added only where two options were weighed. `## Consequences` is not
  written.
- A decision file is never edited once accepted; a changed decision is a new file that names what it
  supersedes. Files written before the light form keep their sections.
- `spec/decisions/index.md` is generated: `scripts/model decisions` writes it from the files, and
  `scripts/model decisions --check` exits 0 when it is current. Commit it in the same commit as the
  decision.

## Verifying

`scripts/model check` (this plugin; needs `python3 -m pip install clingo`) reads the final layout (`spec/`, `features/` and `.shop/`, decisions included) and prints each rule by its name and
its label: a line with no id (`v15a` (a requirement has no id)), two lines with one id (`v15b` (two requirements share an id)), a retired
id taken again (`v15c` (a retired id is used again)), a line with no scenario (`v_s3` (a requirement has no scenario)), a scenario that names no line (`v_s1` (a scenario names no requirement)), a line not in an EARS pattern or with more than one "shall" or sentence
(`v_e1` (a Behaviour line is not in one of EARS's patterns), `v_e2` (a Behaviour line has more than one "shall" or more than one sentence)), a word the glossary avoids, or a glossary at odds with itself (`v_t1` (a word the glossary avoids), `v_t2` (a term has two entries), `v_t3` (an avoided word is a term)), and
references that name nothing. It exits 0 when it finds nothing. When the interpreter running it lacks
clingo, it looks for one that has it (`$SHOPSYSTEM_MODEL_PYTHON`, each `python3` on `PATH` outside the
active virtualenv's `bin/`, `/usr/local/bin/python3`, `/usr/bin/python3`) and re-executes itself under the first it
finds. When none has it, it exits 2 with a message that names clingo, `pip install clingo` and each
interpreter it tried; coverage is then verified by hand.

## Doing it

1. Read the note and list its capabilities: clusters of behaviour with one
   narrator. Ten give or take is normal for a component.
2. One file per capability. Put the note's sentences into the four
   sections; cut what fits none.
3. Rewrite Behaviour as EARS lines. Each line you can't give an observable
   response to goes to Implementation. Each condition the note never
   gave becomes either a line or a question — write the questions down.
   Number the lines `[r1]` on in each capability.
4. Write `spec/index.md`: frontmatter `id: bounded-context/<context path>`, the context path
   being `<owner domain>/<product>/<context name>` (ask the person when you do
   not know them) and `title`; then purpose, constraints,
   composition (the capabilities in reading order), order of building,
   testing, and the Glossary in the form above. Any table spanning capabilities is rendered from them, not
   authored.
5. Write the note's decisions as decision files in `spec/decisions/`, then run `scripts/model decisions`.
6. Formulate one feature per capability, one scenario per line.
7. Keep the note as a dated proposal; from here the capability files are
   the spec. A later note is integrated into the same `spec/`: it never
   starts a second one.

## Not in stage 1

- Relationships between contexts, `@uses` tags, requests. Until the
  partnership with the neighbouring repo ends, cross-citation in feature
  files is fine.
- Capability groups (model / service / operations / guarantees). A column
  to add when the list gets long enough to need it.
- Beliefs. Rationale goes in the decision that gives it.
- Tooling beyond scripts/features and scripts/model. The pairing is a naming convention, a header comment and the @r<n> tags.
