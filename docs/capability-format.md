# Capability files and their generated feature files

Date: 2026-09-29 (stage 1; adopted by the plugin in 0.8.0); requirement ids 2026-10-16 (0.19.0); final layout,
decision files and ids for references 2026-10-19 (0.21.0); codified requirements 2026-11-03 (1.0.0, design model v5)
Scope: one context, on its own. Nothing here needs agreement with another repository or a product level.

## What this is

A context's spec is a set of capability files. Each capability's behaviour is written as **codified
requirements**: sentences in a controlled English whose words are the context's glossary and whose shapes are the
six EARS forms. Every requirement parses to exactly one tree in the context's grammar, or it is refused before
anyone reads it. Requirements sit in **requirement groups**; each group is one scenario, and the scenario is
**generated** from the group by `features generate`, never written by hand.

What you get: a line that admits two readings does not parse, so the question it would have raised is answered
while the line is written; the requirements of a context are checked together for contradictions by
`model logic`; and features cannot drift from the spec, because they are a function of it.

## Layout

```
spec/
  index.md              the context: purpose, constraints, composition, testing, the glossary (typed terms)
  universal.md          the universal conditions U<n>, true on every trace
  restated.json         the 0.29 ids and their text, frozen at the conversion (only in a converted repository)
  decisions/
    <nnnn>-<slug>.md    one file per decision
    index.md            generated by `scripts/model decisions`, never written by hand
  capabilities/
    identity.md         one file per capability
    ...
features/
  identity.feature      generated, one per service capability, same name
.shop/                  how the context is changed and what was noticed
  backlog/  batches/    the items, and the batches that build them
  requests/  quotes/    requests between contexts; the person's words kept
  records/              observations, measurements, review findings, archive
  work/                 plugin 1.x's queue of initiatives and work-items, frozen as history
  scratch/              drafts and notes of a session; git-ignored, never read as the model
```

The pairing is by name: the capability `identity` (`spec/capabilities/identity.md`) generates
`features/identity.feature`. A guarantees capability has no feature file: its requirements parse and are
logic-checked, and measurement or trials check them.

**Codified, file by file.** A capability file is codified when its own frontmatter says `language: codified-1`, and
`spec/index.md` when its glossary is typed. A file without the marker is read as a 0.29 file (bullets with `[r<n>]`
ids and free English) until `migrate upgrade` converts it; after the 1.0.0 release a file without the marker is
refused, naming `migrate upgrade`.

## The capability file

```markdown
---
id: capability/missingmass.io/shopsystem/shopsystem-bdd/backlog
title: Backlog
narrator: a person or session keeping the backlog
group: service
language: codified-1
rests_on: [design-decision/the-workflow-simplified]
retired: []
---

# Backlog

## Purpose
One paragraph: what this is, and what it isn't.

## Terms
- **title** (noun): the name of an item that the person reads beside its id.

## Relations

| from | word | to |
|---|---|---|
| title | of | item |

## Behaviour

### [g2] `work shape` shapes an idea
Restates: r3@0.29, r4@0.29.
- [r2] When the person runs `work shape` on an item that is `idea`, `work` shall set the status of the item to
  `shaped` and print the item.

## Implementation, may change
Mechanism. Non-binding. Nothing here gets a scenario.

## Not yet
Deferrals, each with the trigger that promotes it.

## Dropped
- r7@0.29: restated U3 (a refusal changes nothing).
- r12@0.29: moved to supervision.
```

Every sentence in the file is one of five kinds, and the section it sits in says which:

| kind | section | falsified by |
|---|---|---|
| decision | `spec/decisions/`, cited by `rests_on` | argument, or its `revisit_when` |
| term | Terms (or the index's Glossary), and the rows of Relations | a line that needs another word |
| requirement | Behaviour | its group's scenario, or `model logic` |
| implementation | Implementation, may change | measurement |
| scope | Not yet | its trigger firing |

A sentence that is none of these — rationale, intent, a comparison to what was rejected — is cut from the
capability. If it matters, it goes in the decision it explains. `## Dropped` is a record written once by the
conversion and kept: each 0.29 id that no group restates, with its reason or `moved to <capability>`.

## Writing requirements

**The forms.** One sentence, the clauses in this order. The actor is a glossary actor, and the response is
`shall` and its verb phrases joined by `and` (`shall A and B`, `shall A, B and C`), or `shall not` and verb
phrases joined by `or` (`shall not A or B`: neither):

| form | shape | its scenario |
|---|---|---|
| ubiquitous | `Actor shall V.` | Givens from its noun phrases' restrictions, then Then; no When |
| event-driven | `When T, Actor shall V.` | When T, Then V |
| state-driven | `While C, Actor shall V.` | Given C, Then V |
| optional feature | `Where F, Actor shall V.` | Given F, Then V |
| unwanted behaviour | `If T, then Actor shall V.` | Given or When the invalid input, Then V |
| complex | `[Where F,] [While C,] When/If T, Actor shall V.` | the clauses in order |

**The form follows what starts the behaviour.** A response to a command, an input or an event is event-driven.
A refusal is unwanted behaviour. Behaviour that lasts for a period is state-driven. Behaviour that depends on an
option or configuration is optional. Only what is true with no trigger at all is ubiquitous.

**One statement for each trigger and condition.** Everything that happens under one Where, While and When/If is
one statement: its verb phrases are joined by `and` (`work` shall set the status of the item to `shaped`
and print the item), and responses whose subjects differ by `, and` (`R1, and
R2`). Each verb phrase is its own Then in the scenario and its own conjunct in the logic, under the one requirement
id. A list response ("shall print the id and the title") is one verb phrase with a coordinated object. A condition
may join its clauses by `and` or by `or`.

**Only lexicon words.** Every word of a requirement is a glossary word, a grammar word (the forms, `shall`, the
articles, `and`, `or`, `not`, `every`, `at most`), a backticked code (`` `work shape` ``, `` `.shop/backlog/` ``), a
double-quoted string or a number. A value goes only in its own attribute's slot: "an item that is
`building`" does not parse, because `building` is a value of a batch's status. Where a word is missing, the line
asks for a glossary entry; a synonym never stands in for it.

**Check while writing.** `model parse "<line>"` (or `--file <lines>`) prints the tree, or the refusal with the
token, its position, the longest prefix that parsed and the nearest lexicon words. `model lexicon` lists the words
by category. A request's lines are checked the same way by the upstream's `work outcome accepted`.

**What not to write.**

- A refusal changes nothing, a transition is committed and pushed, `--json` prints one object: these are
  universal conditions (`spec/universal.md`), checked on every trace and never restated in a requirement.
- Exclusivity is never "one at a time, except …": a resource of the glossary is `exclusive` or `counted by`
  its number, and what holds it is a requirement.
- Exits are in words (`shall exit successfully`, `shall exit with an error naming …`), never a code
  (design-decision/exits-are-successful-or-errors).

**The response is observable by the narrator.** A value printed, a refusal and what it names, a file at a path, a
status set. If you can't write the response that way, the sentence is implementation and goes down a section.

## Groups

A group is the one statement that makes one scenario: its pre-state (Where, While), its trigger (When, If) and
its responses joined by `and`. A group has one statement (v15l), and two groups of one capability never share
their features, condition and trigger (v15n): they are one group, with `and` between their responses. With one
statement in each group, a group `[g<n>]` and its requirement `[r<n>]` share their number. A group has a title in
free English, not parsed, which is the scenario's title, and two optional parts:

- `Restates:` the 0.29 ids it replaces, one line, sorted, `r<n>@0.29` for its own capability's and
  `<capability>#r<n>@0.29` for another's. Only a converted repository has them; `model restates` checks that every
  0.29 id is restated, dropped or moved.
- a fenced `given` block of **example data** only: the contents of a file, a table, a text the requirement names
  but does not carry, put before the generated Givens. Everything else a scenario starts from (an instance, a
  value, a condition) comes from the statement itself: "While a work-item is `drafted`" gives the Given "a
  work-item w1 that is `drafted`". A given line is example data by its shape alone: `the <words> <name> holds:`
  followed by a docstring or a table (the lines indented two spaces under it: lines starting with `|` are its
  data table, any other lines its docstring), or `the <words> <name> holds` followed by exactly one code span or
  quoted string. `model check` reports any other given line (v15m); a condition it states belongs in the
  statement, as a While or a Where.

````markdown
```given
the file `spec/index.md` holds:
  ---
  id: bounded-context/ex.com/prod/ctx
  ---
the question q1 holds "Which branch wins?"
```
````

A group whose statements are all resource statements (`holds`, `holds at most`) has no scenario: it is
logic-only, checked by `model logic` alone.

## Ids

- Requirements are numbered `[r1]` on across the file, groups `[g1]` on, universal conditions `[U1]` on. A new
  one takes the number one above every number the file has used or retired. A group has one statement, so a new
  group and its requirement take one number: `[g7]` holds `[r7]`.
- **Retire, never edit.** A changed requirement is a removal and an addition: the old id goes into the
  frontmatter's `retired: [r<n>, g<n>, ...]` and the new statement takes a new id. A group's title and membership
  may change; its id stays.
- A requirement is named `capability/<context path>/<name>#r<n>`, `capability/<name>#r<n>` or `<name>#r<n>`
  inside its own context; a group `…#g<n>`. An item's `## Requirements` writes the lines it adds into a
  capability, and a scenario is tagged with its group and each member (`@g3 @r7 @r8`).
- A reference written before the conversion names a 0.29 id; it reads `<capability>#r<n>@0.29` and is resolved
  through `spec/restated.json`, never against the live spec.

Ids are type-first: `<kind>/<context path>/<name>`, the context path being the owner's domain, the product and
the context name (`missingmass.io/shopsystem/shop-kb`). The bounded context is `bounded-context/<context path>`,
`spec/index.md`'s `id`. A capability is `capability/<context path>/<name>`; a decision
`design-decision/<context path>/<slug>`. A frontmatter `id` is always written in full. A reference may be shorter:
`<kind>/<name>` inside its own context, and the bare `<name>` in a field that fixes the kind (`rests_on`,
`supersedes`, `argues`, `under`, `depends_on`). A frontmatter field names another file by its id, never by a path.

## The glossary is the lexicon

A context's terms are its words. The glossary is the union of `spec/index.md`'s `## Glossary` and each
capability's `## Terms`, in one entry form, each entry naming its **part of speech** in parentheses, which gives the
**category** — the grammar slot the word fills.
The example below is from plugin 1.x's vocabulary, kept as an illustration of every category:

```markdown
- **node** (noun): a root or a part of the work queue.
- **initiative** (noun): the delivery of one request's accepted lines. Plural: initiatives. Kind of: node. Not: epic.
- **status** (attribute of initiative): an initiative's place in its lifecycle. Values: `proposed`, `started`, `done`, `abandoned`.
  Transitions: `proposed` → `started`: `work start`; `started` → `abandoned`: `work abandon`; `started` → `done`: complete.
- **open** (adjective of initiative): An initiative is open when the initiative is not `done` and the initiative is not `abandoned`.
- **unfixed** (adjective of initiative): an initiative whose kept branch review lists a finding to fix now.
- **start** (verb): the beginning of a stage. Forms: starts, started.
- **spec lock** (noun, exclusive): the lock every integrate, apply and formulate round holds.
- **worker slot** (noun, counted by `workers`): one of the workers `.shop/delivery.toml` allows.
- **`work run`** (proper noun): the supervisor that runs nodes through their transitions.
```

| part of speech | category | what it is | in a requirement |
|---|---|---|---|
| `(proper noun)` | actor | what a `shall` is about | the subject of `shall` |
| `(noun)` | kind | a sort of thing with an identity | a noun: `an initiative`, `every work-item` |
| `(attribute of <kind>)` | attribute | a property of a kind with closed values | `whose status is …`, `that is `started`` |
| (in `Values:`) | value | one value of one attribute of one kind | only in its attribute's slot |
| `(verb)` | event | something that happens at one step, with its `Frame:` | a trigger or a response |
| `(noun, exclusive)`, `(noun, counted by …)` | resource | what a session holds while it runs | `holds`, `is free` |
| `(adjective of <kind>)` | condition | a named clause | one word for a long condition: `an open initiative` |

A relation is no term entry: it is a row of `## Relations` (below).

- **One sentence for each entry** (v_t7). The gloss is the text after the entry's `:` and before its first field.
  Code spans, quoted strings, `e.g.`, `i.e.`, `etc.` and `vs.` are not counted; a sentence ends at `.`, `!` or `?`
  before a space or the end, and at `;`; a `:` does not end one. The gloss says what the word picks out, never what
  the thing contains or does: "**title** (noun): the name of an item that the person reads beside its id." What an
  item, a list or a log holds, and what happens to it, are requirements of the capability ("When the person runs
  `work idea`, `work` shall write an item that is `idea` and commit the item.").
- The fields are data, not sentences: `Values:` and `Transitions:` (an attribute), `Forms:` and `Plural:` (only
  where English is irregular), `Not:` (avoided words) and `Kind of:` (a kind's supertype). There is no other field.
- The part of speech is required (v_t4); plugin 2.x's categories (`(kind)`, `(actor)`, `(event)`, `(condition of
  …)`, `(resource, …)`) name none, and `model lexicon --check` gives each one's part of speech. An attribute or
  condition names its kind: `of <kind>`.
- A value belongs to exactly one attribute of one kind (v_t5); the same word in two attributes is two values, which
  the typed slots keep apart. No two terms of one category linearise the same (v_t6).
- `Values:` and `Transitions:` (each `from → to: <event, command or condition>`) give an attribute's lifecycle;
  `model logic` allows a status to change only along a row.
- A word with entries for several kinds (`status` of each kind with a lifecycle) is defined once: one entry
  carries the sentence, and the entries for the other kinds give their own fields.
- `Not:` lists the words the context avoids for that thing; `model check` reports one in a prose section (v_t1).
  Once every capability is codified, a requirement can only use lexicon words anyway.

**Conditions.** A condition's entry is one sentence, and it is either a definition or primitive:

- **A definition** is a sentence in the language: `A <kind> is <condition> when <clauses>.`, its clauses joined by
  `and` or `or`, naming its subject as "the <kind>", never "it" (`open` above). It parses in the `Def` grammar
  (`model parse --grammar Def "<sentence>"`), and `model logic` reads it as the condition's rule. A condition that
  tests a value is always a definition. A coordination across two kinds is two clauses: "A result is outputless
  when the result gives no question and the result gives no output."
- **A primitive** condition is one whose sentence does not parse as a definition, because its words (a bullet, a
  bracket) are not lexicon words (`unfixed` above). Its sentence is a gloss, like a kind's; the logic treats it as
  a fact of the thing, chosen when the thing is created and kept after, and a step definition builds it.

A condition is defined when every word of its sentence is a lexicon word and the sentence parses; otherwise it is
primitive. There is no prose `Means` field (v_t9).

A term is standing, approved like a requirement. Its id is `term/<context path>/<term>`, lowercased with spaces as
hyphens. A term change rides with the item that needs it, as a term bullet of its `## Requirements` (`work line
<item> --into <cap> --term`), and adds to `spec/index.md` unless it names a capability.

The grammar itself — the EARS forms, the verb phrases, the typed slots — is the plugin's (`grammar/`), and grows
only in the plugin. A context grows its language by glossary entries and relation rows only.

## Relations

The relations of a context are one table, `## Relations` in `spec/index.md`; a capability may add its own local
rows under its own `## Relations`. A row is `| from kind | word | to kind |`, with an optional fourth cell for
cardinality (`one`), and nothing else: no gloss. The word is a preposition (`for`, `on`, `with`, `of`) or a verb
written as the clause says it (`fulfils`, `rests on`).

```markdown
| from | word | to | cardinality |
|---|---|---|---|
| stage | for | node | one |
| work-item | under | capability-proposal | one |
| initiative | fulfils | request | one |
```

- **A preposition means the one relation its row gives for the two kinds it joins.** "a stage for the work-item w1"
  is the row (stage, for, node), since a work-item is a kind of node; there is no entry that says what `for` or
  `on` means. Two rows with the same from, word and to are a problem (v_t10), and a relation entry in Terms is one
  too, whatever its word (v_t8). Two relations between one pair of kinds take two words.
- **A row on a supertype** (a kind whose subkinds say `Kind of: <it>`) holds for every subkind, at any depth, and
  for the supertype itself: one row (stage, for, node), not one for each kind of node.
- **Attachment is typed.** In "a `plan` stage for a work-item with the result", `with the result` attaches to the
  stage because (work-item, with, result) is no row. Where both attachments are rows, the line has two trees and is
  refused; it is reworded.
- A relation is used as a modifier ("a stage for the work-item") or as a clause ("the stage is for the work-item",
  "the initiative fulfils the request").

## Universal conditions

`spec/universal.md` holds `- [U<n>] <statement>`, each a ubiquitous, `Where`, `While` or `When` statement in the
same grammar, with frontmatter `group: guarantees` and `language: codified-1`. They are true in every state of
every trace: `model logic` checks each against the requirements that share an event or an attribute with it, and
where one is observable in a test, the
scenario conftest checks it after every scenario that makes its trigger true. A requirement never restates one; a
0.29 line that only restated one is dropped with the U as its reason.

## Upstreams

A context that depends on others names each one in a `## Upstreams` section of `spec/index.md`, one bullet for
each: the upstream's bounded-context id, a colon, the path of its published spec, and `github: <owner>/<name>`, the
GitHub repository whose issues carry the requests to it (`work request` refuses an upstream with none). A request
into an upstream is written in the upstream's lexicon, the glossary its offer quotes, and the upstream parses each
line in its own grammar before it accepts one.

```markdown
## Upstreams

- bounded-context/missingmass.io/shopsystem/billing: ../billing/spec, github: missingmass/billing
```

## The feature file

Generated, never edited: `features generate <capability>` writes it, and `features generate --check` fails when a
feature differs from what the spec generates. The file starts with the header
`# generated from spec/capabilities/<name>.md by features generate; do not edit`, then `Feature: <title>`, then one
scenario per group in group order, tagged `@g<n>` and each member's `@r<n>`.

A scenario is read off its group's requirements, with no solver. `features generate` reads the facts `model logic`
checks (one translation of each grammar fun) by a fixed rule: the statement's Where and While clauses, its defined
conditions and its noun phrases' restrictions give the Givens, the trigger gives the When, and each verb phrase of
the response gives its own Then, followed by the attributes it sets. A condition "no K is v" gives no Given. A noun
phrase with `every` and a restriction gets a contrast: one more instance that fails the restriction, as a Given, and
a `does not` Then for it. A scenario states only its own requirements, so a requirement added elsewhere changes
nothing in it; the world the handlers build supplies the defaults. A group's example data comes first, from its
`given` block. Every step is a sentence of the step grammar, and the same spec gives the same bytes. Instances are
named by their kind's first letter and a number in order of first mention (`i1`, `w1`), and every step names the
kind: `an initiative i1 that is `proposed`` where it is introduced, `the initiative i1` after. A group with a fact
no step words gets no scenario: `features generate` names the group and the reason on stderr and writes the rest;
`model check`'s row for a group with no scenario (v_s3) is its error. `features generate` exits 1 on a requirement
that does not parse or an example-data line the step grammar refuses.

A scenario that looks wrong is a wrong requirement (back to the spec, in an item) or a defect of the plugin's
grammar or generator (a request to the plugin) — never an edit to the feature file. Step definitions are
handlers, one per (template, term), under `tests/scenarios/<capability>_handlers*.py`.

## Lines that leave nothing to infer

Lessons from 0.22.0's blind formulation that still apply when the grammar refuses what is ambiguous:

1. **Behaviour reaches code only through a requirement.** A fix item that adds behaviour writes its requirement
   first, readied before its batch; a review grades code no requirement asks for Important.
2. **Requirements that touch one thing say which wins, and a requirement names its reach.** Two triggers that can
   both be true at one step and set different values are a contradiction `model logic` reports (L1); name the
   reach ("every pytest command `work batch done` runs") rather than leave it to be inferred.
3. **Anything with states is written as a lifecycle:** each way into and out of each state is a row of its
   attribute's `Transitions:`, and a requirement names the row rather than restating it. `model logic` reports a
   status set by no row (L3) and a pre-state no path reaches (L4).
4. **A word a requirement depends on is a glossary term.** The grammar enforces it: a word outside the lexicon
   does not parse.

## Decision files

A decision is one file, `spec/decisions/<nnnn>-<slug>.md`, `nnnn` one above the highest number in the
directory. The form is light (design-decision/light-decisions): frontmatter, then a title and a Decision section.

```markdown
---
id: design-decision/missingmass.io/shopsystem/shop-kb/delete-refuse-only
summary: "The only delete rule is refuse: a delete that would leave a reference dangling is refused."
date: 2026-09-23
status: accepted
supersedes: [design-decision/delete-cascade]
revisit_when: a request asks for cascade or detach
source: [initiative/delete-rules, observation/2026-09-20-dangling-refs]
by: "the person, 2026-09-23, on the kb design note"
---

# 0007. Delete refuses only

## Decision

The only delete rule is `refuse`.
```

- Frontmatter: `id`, `summary` (one sentence, required), `date`, `status` (`proposed`, `accepted`, `rejected`,
  `superseded`), and where they apply `supersedes`, `revisit_when`, `revisit_signal`, `source` and `by`.
- `source` lists ids of nodes in the repository; everything else it came from is written in words in `by`.
- A decision file is never edited once accepted; a changed decision is a new file that names what it supersedes.
- `spec/decisions/index.md` is generated by `scripts/model decisions`; commit it with the decision.

## Verifying

- `scripts/model check` reads the final layout and prints each rule by its code and label: ids (v15a–v15k), the
  groups' shape (v15l a group with more than one statement, v15m a given line that is not example data, v15n two
  groups of a capability that share features, condition and trigger), the parse (`v_p1` a requirement does not
  parse, `v_p2` it has more than one tree, `v_p3` a `given` line does not parse), groups and scenarios
  (v_s1–v_s4), terms (v_t1–v_t10: v_t7 an entry of more than one sentence, v_t8 a relation entry (a relation is a row),
  v_t9 a `Means` field, v_t10 two relation rows with one from, word and to), and references that
  name nothing. It exits 0 when it finds nothing. `scripts/model lexicon --check` prints the term problems alone.
- `scripts/model logic [<capability>]` checks the requirements together. Each statement is translated, fun by fun,
  into ground facts about it (its roles, pre-state, trigger, responses and sets), and the whole context is checked in
  one clingo solve of the fixed encoding `grammar/check.lp` over the pairs of requirements that share vocabulary
  (a trigger, a kind, an event or an attribute), with one generic instance a noun phrase. A capability filters the
  findings to those that name it; it exits 1 on an error:
  - L1 (error): a clash: two requirements that fire on one trigger in one consistent pre-state and demand opposite
    things, named both, with the merged pre-state of the witness; or one requirement that contradicts itself;
  - L2 (warning): two statements that say the same thing;
  - L3 (error): a set where no transition row allows it;
  - L4 (warning): a value some pre-state needs that no transition path reaches from an initial value;
  - L5 (warning): an untriggered positive event obligation ("While C, X shall do E"), naming the requirements that
    react to its event;
  - L0 (error): the check did not finish within its 20 s limit; the findings found so far are listed.
- `scripts/model restates [<capability>]`, in a converted repository: every 0.29 id restated, dropped or moved.
- `features generate --check`: every feature file is what its capability generates. A scenario is read off its
  group's requirements' facts, with no solver.

The grammar tools (GF, its pgf runtime and clingo) are installed by `tools install`; `tools probe` reports them.

## Doing it

For a new context:

1. List the capabilities: clusters of behaviour with one narrator.
2. Write `spec/index.md`: frontmatter `id: bounded-context/<context path>`, `title` and `language: codified-1`;
   then purpose, constraints, composition, testing, the glossary — the actors, kinds, attributes with their
   values and transitions, events, resources and conditions the behaviour needs, one sentence each — and the
   `## Relations` table.
3. One file per capability, `language: codified-1`. Put each sentence in its section; cut what fits none.
4. Write Behaviour as groups, one statement each, checking each with `model parse` (a condition's definition with
   `model parse --grammar Def`); write the relations as rows of `## Relations`. A sentence you cannot give an
   observable response to goes to Implementation. A word you lack becomes a glossary entry; a condition nobody
   gave becomes a requirement or a question.
5. Run `model check` and `model logic`, then `features generate` for each service capability.
6. Write the decisions as decision files and run `scripts/model decisions`.

For a repository on 0.29: `migrate upgrade` converts it one capability at a time (a scaffold of one group per old
line, `Restates:` filled), and a session writes the codified requirements.
