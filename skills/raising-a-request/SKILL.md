# Raising a Request

## Overview

A request is a conversation on one GitHub issue on the upstream's repository, and every step is a comment a `work` command posts. It opens with the asker's need in its own words (`work request`); the upstream offers the capabilities that may serve, with the words they use; then the asker either says one fits (`work fits`) or proposes lines (`work propose`). A request's lines are codified requirements: each parses to one meaning (its logical form) in the grammar 4 of the context it goes to, built from that context's layers (the base grammar, the packs its `spec/index.md` imports, and its vocabulary, each word naming an element of its domain model), and the upstream refuses to accept one that does not. This skill turns the person's English into lines in the upstream's terms. It writes no spec and decides nothing: a line is a proposal, and the upstream judges it.

Scripts: `<this skill's base directory>/../../scripts/`. The upstream's terms are the vocabulary its offer quotes (under the request's `## Offer`). Where the upstream's spec is at hand, run every `spec` command with `--root <the upstream's repository>`; its lexicon decides, never ours. The language's reference is the plugin's `grammar/language.md` (the reading rules R1-R12 and each construct, with real lines and their logical forms) and `grammar/constructs.md` (the construct catalogue: each construct's code, form and example), at `<this skill's base directory>/../../grammar/`. Nothing reads or writes the upstream's repository.

## The forms

One sentence, the clauses in this order (`grammar/language.md`, R9; `grammar/constructs.md`, `when` to `where`):

| the person says | form | shape |
|---|---|---|
| when someone runs or something happens | event-driven | `When T, Actor shall V.` |
| while something holds | state-driven | `While C, when T, Actor shall V.` |
| it refuses, or fails safely | unwanted behaviour | `[While C,] If T, then Actor shall V.` |
| it is never done, or done only so | prohibition, restriction | `Actor shall not V.`, `Actor shall V only Ks that P.` |
| it is so by definition | necessity | `A K always/never ...` |
| it is allowed | permission | `Actor may V.` |
| a feature the product is built with | optional feature | `Where F, [while C,] when T, Actor shall V.` |

A line that obliges with no trigger, and neither "always" nor "never", is refused (R12): a `shall` that obliges needs a When or an If; `shall not` and `only` stand alone. The form follows what starts the behaviour, not the person's wording. What happens under one trigger and condition is one line, its verb phrases joined by `and`:

```
While the status of an item is `idea`, when the person shapes the item, the backlog service shall set the status of the item to `shaped`.
If the person enters a design-decision without a tier, then the decisions service shall refuse the request and name the tier.
While the status of an item is not `idea`, if the person shapes the item, then the backlog service shall refuse the request and name the item.
```

`shall A, B and C` lists more; `shall not A or B` forbids both; `R1, and R2` joins responses whose subjects differ. A condition's clauses join by `and` or `or`. A preposition (`of`, `in`, `on`, `for`, `with`, `from`, `to`, `by`, `at`) means the one relation the context's domain model gives for the two objects it joins (`has → K` reads "of", `holds → K` reads "in"; cardinality `one` makes it functional); a line with two readings that mean different things is refused, naming the words. A response is what the service answers: it returns, keeps, completes, fails a check, refuses the request and names a reason, notifies; never an exit code, a printed layout or `--json`, which are the CLI adapter's. Never restate what `spec/universal.md` holds: `spec explain` shows what a line means through them.

## Writing a line in grammar 4

The rules of the controlled language 4 (`grammar/language.md` reads each with real lines):

- **Plain words in sentence structure, no coined adjective.** A state is said with the structure that holds it, from the lexicon's own words: "a comment that does not conform to the comment form", "an item whose status is not `shaped`", "a commit that cites no item", "a request that holds no comment". A new adjective is a state missing its structure. An adjective that stays is defined by a sentence of the grammar (`- **open** (adjective of initiative): An initiative is open when the initiative is not `done` and the initiative is not `abandoned`.`), never by prose.
- **States in While, behaviour in When or If.** A state verb (`(verb, state)`, "has V-ed") goes in a While clause or a relative clause; an action verb (`(verb, action)`) in the trigger and the response; a verb of the wrong aspect there is refused. A state put into the trigger's noun phrase moves to While: "While an item is `shaped`, when the person readies the item", not "when the person readies a shaped item".
- **The agent explicit.** Every trigger and response says who acts: the person, a session, a service ("the backlog service"), a clock. No passive ("when an item is readied").
- **A request, never a command.** The trigger is a request of an operation of the domain model, said with the verb the vocabulary gives it: "the person shapes the item", "the person enters a design-decision". Its parameters follow its object: "with a note", "with the tier `check`", "with the reminder" (a flag), "without a tier". A command, an option, `--json`, an exit code and a printed layout are the CLI adapter's (`spec/adapters/cli.toml`), never a line's; the CLI pack is retired. Never "Where `--x` is given": Where is a feature the product is built with.
- **A refusal is short:** "If ..., then the backlog service shall refuse the request and name X". That it changes nothing and names a reason is entailed (U17); `spec explain` shows it, and the generated scenario writes it as a `# entailed:` comment. Each refusal reason the operation declares in the model (`refused: no tier`) needs its line (`v_m4`).
- **"the K" names something the line gave**: an earlier noun of the line, "the K of X" over a relation or an attribute, or a kind whose entry has `This:` ("this repository", "the request"); else the line is refused, naming the noun (R2). "its" binds to its clause's subject (R8).
- **"does not V a K" in a condition is refused** (R4): say "Vs no K" or "a K that X does not V". "a K" in a condition or trigger is any K; in a response, a new one (R1). "one K" is exactly one; counts as "at least two Ks", "the number of Ks is at least n" (R7, `count`, `number-of`).
- **Example data goes in the group's given block**, never in the line. A line names kinds and declared constants (actors, services, values, rule and construct codes, named instances); a code or quoted string that names none (a path, a message text, a sample value) is a parameter that the given block binds, and `spec check` warns of it (`w_example`).
- **A format is an artifact the line conforms to**: "a comment that conforms to the comment form", "a file that does not conform to `grammar/language.md`". The artifact is an element of the model with its vocabulary entry.
- **A line about the language or the check names its code**: a construct by its code in `grammar/constructs.md` ("a requirement that uses `rc-object`"), a rule by its code in `grammar/rules.md` or `spec rules` ("a term that violates `v_t11`"), with the spec pack's words (`imports: [request, spec]`); never a coined word for a construct.
- **A value in the full form unless it is an adjective.** "the status of an item is `idea`", "an item whose status is `idea`" take any value; the short form "an item is `shaped`" only a value whose vocabulary entry is an adjective (`- **shaped** (adjective) → value item.status shaped.`). A value whose entry is a noun (`idea`, `needs-input`, `check`, `0.30.0`) in the short form is refused, naming the full form; reword to it. A new attribute's values are the model's (`tier: check | requirement | judgement`), each value named by an entry as an adjective or a noun.
- **Compounds and attributive nouns.** "the batch status" is "the status of the batch" (an attribute), "a request comment" "a comment of a request" (a relation row); a compound that is a thing of its own ("proposed change") is a declared noun. A declared attributive noun tells two things apart ("http status" against "batch status", "work item").
- **A verb names one element.** An action verb names an operation (`- **shape** (verb, action) → operation backlog.shape. Frame: <actor> shapes <item>.`), a state verb a relation; its thin `Frame:` gives word order and prepositions, its kinds come from the model. The kinds of a line's nouns pick the frame; a noun of the wrong kind is refused, naming the verb's frame.

## Process

1. **Find the words.** `python3 <scripts>/spec lexicon` lists the context's terms by category: actors (the subject of `shall`, services and proper nouns among them), kinds, attributes with their values, events (verbs, a pack's marked `[pack request]`). The model (`spec/model/<area>.md`) says what each may combine with: each service's operations and their parameters, each object's attributes, lifecycle and relations. The packs `spec/index.md` imports (`imports: [request, spec]`) bring the words of a request and its response (request, parameter, service, reason, response, check; refuse, name, return, notify, complete, fail, keep, change, conform, start) and of a spec (requirement, construct, rule, use, violate); the plugin's packs are `grammar/packs/<name>.md`, a context's own `spec/packs/<name>.md`. Use a value only in its own attribute's slot. Paths are backticked codes, message texts double-quoted strings; a path, a message text or a sample value the lexicon does not declare is example data (Writing a line, above). `python3 <scripts>/spec constructs --check` says whether the catalogue is current; read the construct you need in `grammar/constructs.md`.
2. **Write the lines**, one per line in a file, in the person's order: `<scratch>/request-lines.md`.
3. **Check every line** with `python3 <scripts>/spec parse --file <scratch>/request-lines.md`. Each line prints its tree, or its refusal: the token and its position, the longest prefix that parsed (`parsed up to:`), the nearest lexicon words and the words that `may follow`; or the rule that refuses what parsed (an unbound "the", "does not V a K" in a condition, a verb of the wrong aspect, a line with no trigger, two readings that mean different things), naming the words. Then run it again with `--form`: each line's logical form, its referents (constants, parameters, the request's own things), its request (`request(e1, <service>.<operation>, ...)` with its `param`s) and its While, trigger and response boxes. Read it against what the person meant: a `the` bound to the wrong noun, a state in the wrong box, is a line that parses and means something else. The example data that goes into a given block is what `spec check`'s `w_example` names (a path, a message text, a sample value).
4. **Reword from the refusal.** Reword at the refused token, starting from the prefix that parsed, with one of the nearest words when it means what the person meant. A line refused for two readings is split or made specific at the words it names. A state in the trigger's noun phrase goes into While; a command or an option becomes the request and its parameters; a long refusal ("refuse the request, name X and change nothing") becomes "refuse the request and name X"; example data goes into the given block (on an item here, `work line --given`; for an upstream, the line names the kinds and the upstream writes the given block). Run step 3 again until every line parses and its form says what the person meant.
5. **A missing word is a model element and its vocabulary entry, never a synonym.** When the person means a thing the lexicon has no word for, do not bend the line onto a nearby word that means something else. Tell the person which word is missing, and write what the context would need: the model line (`object label`, `service backlog` with `operation tag(item, label)  outcomes: done`, `item: has → label (many)`) and the vocabulary entry naming it, one sentence, its part of speech one of `noun`, `proper noun`, `adjective`, `attribute`, `verb, action` or `verb, state`: `- **archive** (verb, action) → operation context requests.archive. Forms: archives, archived. Frame: <actor> archives <context request>.` A word a pack the context imports defines too carries `Redefines: <pack>.`; a kind whose "this K" is the request's own carries `This: <gloss>.` A state with no word is a structure of words the lexicon has (Writing a line), not a new adjective. In this repository the model line goes into an item with `work line <item> --into <cap> --model "<lines>"` (a relation with `--relation "<object>: <phrase> → <object> (<cardinality>)"`) and the entry with `--term "<entry>"`; for an upstream, ask the person to raise it with its owner, and give them in the request's `--source` note. The line that needs the word waits until the word exists, since the upstream cannot accept it until then. Write every word a set of lines needs before checking them: each change to the vocabulary or the model recompiles the grammar, which takes minutes, so words go in at once and the lines are checked after, not a word between two checks.
6. **Show the person the lines** beside their English, each with what it means: its logical form (`spec parse --form`) read back in plain words, and for a line already in a capability `python3 <scripts>/spec explain <capability>#r<n>`, which prints what it also means (through a universal condition) and each line that takes precedence over it, and change what they say. The lines are the person's.
7. **Ask first**, in this repository: `python3 <scripts>/work request "<title>" --from <this context's id> --thread <job-thread> --ask "<the need, in the person's words>"` (`--to <upstream>` when there are several). It opens the issue on the upstream's GitHub repository (its `github: <owner>/<name>` under `## Upstreams`) and writes `.shop/requests/q<n>.md`. `python3 <scripts>/work sync` records the upstream's offer when it comes.
8. **Wait on the upstream with a watch.** While a request waits on the other side (`work sync` prints `waiting on the other side`), start `python3 <scripts>/work watch --forward` with the Monitor tool (its timeout at the maximum), in place of Bash `run_in_background`: it takes GitHub's events on each repository the account administers (`gh webhook forward`, the cli/gh-webhook extension, installed if missing), polls GitHub's notifications for the others (an upstream's repository) and says which on stderr, and ends, printing one line for each, when the other side posts a comment a request does not hold or a new ask arrives. When it ends, run `python3 <scripts>/work sync`, then this skill's step for each request it named, then start the Monitor again; start it again too when it times out, and after each `work sync`. Stop once no request waits on the other side. A comment it has printed once is not printed again, and it writes nothing. Say to the person that the session is watching.
9. **Answer the offer.** When an offered requirement serves the need: `python3 <scripts>/work fits q<n> --serves <capability>#r<n>`, which delivers the request and closes the issue. Otherwise write the lines (steps 1-6) in the offer's terms and propose them: `python3 <scripts>/work propose q<n> --line "<line>"` (once a line), answer questions with `python3 <scripts>/work reply q<n> <k> "<answer>"`, and post the turn with `python3 <scripts>/work turn q<n>`. A line the upstream refuses or rewrites comes back with `work sync`; go back to step 4.

## Red Flags

| Seen | Fix |
|---|---|
| A line proposed without `spec parse` run on it, the upstream's spec at hand | Step 3 first; the upstream refuses to accept what does not parse |
| The person asked to nudge the session when the upstream answers | Start `work watch --forward` with the Monitor tool (step 8) |
| Lines given at `work request` | The ask is words; lines follow the offer, with `work propose` |
| A synonym chosen because the right word is missing | A missing word is a model element and its entry (step 5) |
| A value in another attribute's slot (`a batch that is `shaped``) | `spec lexicon`: each value belongs to one attribute of one object |
| Our vocabulary used for an upstream's request | `--root <the upstream>`: its lexicon decides |
| Two lines with the same trigger and condition | One line, `shall A and B` |
| Two behaviours in one line joined by "and then" | `and` joins responses to one trigger; a later step is its own trigger and its own line |
| A command, an option, an exit code, `--json`, a message's exact words, or a field name in a line | The request and the response in the domain's words; the rest is the adapter's or the implementation's |
| A new adjective for a state (`unreadable`, `misversioned`) | The structure that holds it: "a comment that does not conform to the comment form" |
| A noun value in the short form (`an item is `idea``) | The full form: `the status of an item is `idea``; `spec lexicon` shows each value's kind |
| A state in the trigger's noun phrase (`on a shaped item`) | `While an item is `shaped`, when ... on the item` |
| `Where `--json` is given, ...`, or `runs `work backlog`` | The request: `when the person lists the backlog`; `--json` renders every response |
| `shall refuse the request, name X and change nothing` | `shall refuse the request and name X`; the rest is entailed (U17) |
| A sample value (`m1`, "banana") in a line | It goes in the group's given block; the line names kinds |
| A passive, or no one who acts (`when an item is readied`) | Name the agent: the person, a session, a service |
| A construct or check named by a coined word | Its code: `uses `rc-object``, `violates `v_t11`` |
| `spec parse --capability` or `--grammar` | Gone: `spec parse` reads grammar 4 from `spec/index.md` |
| A line that parses, its form not read | `spec parse --form`: a parse is not a meaning |
| A word added, `work ready` run, another word added | Every word first, then one check: each vocabulary change recompiles |
