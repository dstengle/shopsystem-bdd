# Shaping Items

## Overview

A brainstorming ends in shaped items whose requirement lines pass the readiness bar, not in a long design document. The session writes the lines and readies the items; the person may skim the lines in the backlog and in the pull request. Do not ask the person to approve the lines: nothing waits on their reading.

An item's lines stay on the item (its `## Requirements`) until its batch merges; `spec/` is not written. `shop work ready` checks them on a copy of `spec/`: every line parses to one meaning in the context's grammar 4 (its capability's terms and the item's laid in), `shop spec logic` finds no L0 nor an L1 naming them, `shop features generate` writes their scenarios, and every request line of the item is settled.

Scripts: `<this skill's base directory>/../../scripts/`. For larger work a design record is still written, beside the items, never in place of them. A design-decision it settles is written with `shop work decision` (`--help` gives its fields), and `shop spec forms` names the command for any other file.

In this repository this skill wins over superpowers:brainstorming's ending: when both fire, the brainstorming ends here, in items with lines, not in "write the design doc" and a plan. A design record may sit beside the items.

An item's own line is reworded by `python3 <scripts>/shop work line <b> --reword <capability>#r<n> "<the new line>"` (same id and group) and taken out by `python3 <scripts>/shop work line <b> --remove <capability>#r<n>` (its group too when it was the last line, and the id it retires), each committing the item; never by editing the bullet. A ready item's lines change once `python3 <scripts>/shop work reopen <b>` has moved it back to `shaped`; `shop work ready` readies it again. A line already in `spec/` is never edited in place: a changed one is a new line that retires it, `python3 <scripts>/shop work line <b> --retires <capability>#r<n> "<the new line>"` (it goes into that capability, its new id into `unbuilt:` and the old id under `retired:` when the batch lays it; a universal condition: `--universal "<statement>" --retires universal#U<n>`). A line that parses unchanged and means the same keeps its id. `shop work line <b> --recodify <capability>` is only for a capability whose file still says `language: codified-1` (`shop spec check` refuses it, naming `shop migrate upgrade`, which switches every file).

- An item with no behaviour a scenario checks (docs, skill text, an agent definition, module-map rows, a test fix, a refactor) is a chore: in place of lines, `python3 <scripts>/shop work chore <b> --file <path> [--file <path> ...] --check "<command>"` names the files (or directories) its work changes and a command that fails now and exits 0 once the work is done (a test, a grep, a command's exit). Run again, it replaces the chore. A path under `spec/`, `features/` or `.shop/` is refused, and a chore and requirement lines exclude each other: an item with behaviour to check takes lines, never a chore beside them. `shop work ready` readies a chore item without running its check; `shop work batch done` runs it.
- A bug in what a delivered item built: `python3 <scripts>/shop measure defect <item> --says "<the fault and how to reproduce it>"` first, then shape its fix as an item.

## A repository with no spec yet

The person never runs the plugin's tools: they are scripts under `<scripts>`, not on their `PATH`. When they ask to set the repository up, or want an app built where `spec/index.md` does not exist yet, the session does it, then goes on to the first item:

1. A git repository (`git init -b main` when it is none) and a virtualenv `.venv` with `pip install 'pytest==9.1.1' 'pytest-bdd==8.1.0'`.
2. The grammar tools once: `python3 <scripts>/shop tools install`, then `python3 <scripts>/shop tools probe`, whose `grammar:` block names GF, pgf, clingo and gf-rgl; a repository with no source file yet still gets them. Show the person that block.
3. The context: ask the person for its id, `bounded-context/<domain>/<path>`, and run `python3 <scripts>/shop migrate init --id <id>`. It writes and commits `spec/index.md` (`language: codified-2`, `imports: [request]`), `spec/universal.md`, the empty `spec/model/`, `spec/vocabulary/`, `spec/capabilities/`, `.shop/`, `features/` and `tests/scenarios/conftest.py`; it refuses where `spec/index.md` or `.shop/` exists, changing nothing.
4. A GitHub repository as `origin` (ask for it, or `gh repo create` on their yes): a batch ends in a pull request there.
5. The first item, as the Process says: `shop work idea`, `shop work quote`, `shop work shape`, then the capability new to the context, `python3 <scripts>/shop work line <b> --capability <name> --narrator "the person" "<its purpose>"` (`--group guarantees` for one that guarantees rather than serves), its model lines with `--into <name> --model "<lines>"`, its relations with `--relation`, its vocabulary entries with `--term` (step 2), then its lines. The item keeps each model line and entry in the new capability's area until its batch lays them into `spec/model/<area>.md` and `spec/vocabulary/<area>.md`; nothing under `spec/` is written by hand. Its first batch makes the program, the step bindings and `spec/adapters/cli.toml` (building-a-batch).

## Shaping several items at once

When a brainstorming settles several items, shape them in parallel: one fresh agent per item, each writing only its own item, all dispatched in one message. Sequence two only when one needs the other's result (a term or a relation row the other's lines use, an id it retires) or when they edit the same file; such items go in later waves. The person's words are quoted (`shop work quote`) and each item written (`shop work idea`, `shop work shape` with its note) by the session before the wave, so an agent starts from an item that exists.

The session fills `parallel-brief.md` (beside this skill) once per wave: the wave's items, each with its number, title and what its lines are to say, and the live directives, printed by `python3 <scripts>/shop work directives`, pasted in verbatim. Each agent's prompt is that brief with its own item named. Its rules are the wave's: the agent touches its own item only; it adds every model line, vocabulary entry and relation first, before it checks a line, since each change to them recompiles grammar 4; it runs a long command (`shop work ready`, `shop spec logic`) with a timeout of a few minutes; it pushes nothing and runs no `shop work batch` command; it never uses `git stash` (every worktree shares one stash list) nor Claude Code's memory. Each agent replies with its item ready, or with its refusal and one question. The session then tells the person afterwards (step 5) and builds (step 6) once the wave is in.

## Process

1. **Write the item.** `python3 <scripts>/shop work idea "<title>"`. For each thing the person said that the item rests on, run `python3 <scripts>/shop work quote "<their words, exactly as they wrote them>"`. It prints `quote-<n> "…"`; on a refusal, copy the words again from their message, or give `--session <id>` for an earlier session: its id is the name of its transcript, `<id>.jsonl`, in the project's directory under `~/.claude/projects/` (newest last by `ls -tr`), or give that file with `--transcript <path>`. Then `python3 <scripts>/shop work shape <b> --note "<the context to work from>, the person's words in quote-<n>"`.
2. **Write each behaviour as a line** (an item with none a scenario checks takes `shop work chore` in place of lines, as the Overview says, and goes on at step 3), the way raising-a-request's steps 1-5 and its "Writing a line in grammar 4" say: plain words in sentence structure (no coined adjective for a state), a value in the full form ("the status of an item is `idea`") unless its vocabulary entry names it an adjective ("an item is `shaped`"), states in While and behaviour in When or If, the agent explicit, the trigger a request of an operation with its parameters ("when the person adds a note without a title"), never a command or an option, a refusal as "shall refuse the request and name X", example data in the given block, a format as an artifact the line conforms to, a construct or a check named by its code. Find the words with `python3 <scripts>/shop spec lexicon` and what they combine with in `spec/model/<area>.md`, check the line with `python3 <scripts>/shop spec parse "<line>"`, read what it means with `python3 <scripts>/shop spec parse --form "<line>"` (and `python3 <scripts>/shop spec explain <capability>#r<n>` for a line it retires or sits beside), and reword from a refusal. A missing word is a model element and its vocabulary entry, never a synonym (raising-a-request, step 5), each written on the item, never into `spec/`:
   - the model lines with `python3 <scripts>/shop work line <b> --into <capability> --model "<lines>"`, in the model's syntax (`object note` with `attributes: title (text); status: kept | removed` and `lifecycle status: kept → removed`; `service notes` with `operation add(title, tag)  outcomes: done → the note | refused: no title`; `actor the person kind of agent`). An attribute's values are the model's (`status: kept | removed`); each refusal reason an operation declares needs its line;
   - a relation with `--into <capability> --relation "<object>: <phrase> → <object> (<cardinality>)"` (`note: under → tag (many)`; `has → K` reads "of", `holds → K` reads "in");
   - the vocabulary entry naming each element with `--into <capability> --term "- **<word>** (<part of speech>) → <element>. <one sentence>."`, the part of speech one of `noun` (→ `object x`), `proper noun` (→ `service s` or `actor a`), `attribute` (→ `attribute x.a`), `adjective` or `noun` for a value (→ `value x.a v`: each value its own entry, an adjective when the short form "an item is `shaped`" may say it), `verb, action` (→ `operation s.o`, with `Forms:` and its thin `Frame: <actor> adds <note>.`) or `verb, state` (→ `relation x.phrase`, with its `Frame:`), and `Redefines: <pack>.` when a pack the context imports has the word.
   - a word the person uses again for another operation keeps the word: a second entry of the same verb names the other operation, with a frame that tells it apart, the object of one and the fixed words of the other (`Frame: <actor> lists <checklist>.` for the notes of one checklist, `Frame: <actor> lists the checklists.` for every checklist, `Frame: <actor> lists the characters of <note>.`), so "the person lists a checklist", "the person lists the checklists" and "the person lists the characters of a note" each read one way. Never a coined verb the person did not say (`browse`). A request acts on one thing: a collection is its frame's own words, not a plural object. The recipe "One verb for several operations" of `docs/recipes.md` shows the entries and their lines.
   They go into the area of the capability `--into` names, a capability new on the item among them. Write all the item's model lines, relations and entries first, then its lines: a word written so is on the item only, so `shop spec parse` still refuses a line that uses it, and the readiness bar (step 4) checks that line with the item's words laid in; each change to them recompiles the grammar there, so they go in at once, before the bar first runs. Then `python3 <scripts>/shop work line <b> --into <capability> "<line>"`; a line of the same scenario as the one before joins its group with `--in g<n>`, and a new group takes `--group "<title>"`. The other spec pieces a line needs go on the item the same way: a group's example data, the sample values a line's parameters take, with `--into <capability> --given g<n> "<given block>"` (one of the item's own groups), a universal condition with `--universal "<statement>"` and an upstream with `--upstream "bounded-context/<path>: <text>, github: <owner>/<name>"`.
3. **Rate it.** `python3 <scripts>/shop work rate <b> --value <v> --urgency <u> --size <s>`, with the reason for each in a note (`shop work shape`'s note, or `python3 <scripts>/shop work annotate <b> "<reason>"` on an open item).
4. **Ready it.** `python3 <scripts>/shop work ready <b>`. On a refusal, reword the lines it names from its reasons (a parse refusal's `parsed up to:`, nearest words and `may follow`, a refusal naming an unbound "the", a verb's frame or two readings, a logic finding's clash, a group with no scenario), with `shop work line <b> --reword <capability>#r<n>` as the Overview says (running `shop work line` again adds a second line beside the bad one), and run it again. A warning (an L3) does not refuse; read it, and reword when the line is wrong.
5. **Tell the person afterwards** which items are ready and what their lines say, in the backlog's words: `python3 <scripts>/shop work backlog` and `python3 <scripts>/shop work show <b>`.
6. **Build it.** With an item `ready` and no batch open, start building-a-batch without asking the person: readying an item is the decision to build it.

## Red Flags

| Seen | Fix |
|---|---|
| A design document written in place of items | The brainstorming ends in items with lines (step 1-4); a design record only beside them |
| Asking the person to approve the lines before `shop work ready` | The bar is the check; tell the person afterwards (step 5) |
| A line bent onto a nearby word because the right one is missing | A model line and its entry, `shop work line --model` and `--term` (step 2) |
| `spec/` edited to hold the item's lines | The lines live on the item until its batch merges; `shop work line` writes them there |
| An item left `shaped` after a refusal | Reword from the reasons and run `shop work ready` again |
| Asking the person whether to ready or batch an item | Ready it (step 4) and build it (step 6) |
| `shop work line` run again to fix a refused line, or its bullet edited by hand | It adds a line; `shop work line <b> --reword <capability>#r<n>` rewords it, `--remove` takes it out |
| A requirement line bent to describe docs, a skill or a refactor | `shop work chore` with the files and a check that fails now and passes once done |
| Two lines with the same trigger and condition | One line, `shall A and B` |
| A new adjective for a state | The structure that holds it, in the lexicon's words (raising-a-request, Writing a line in grammar 4) |
| A command or an option in a line, `Where `--x` is given`, or a long refusal | The request and its parameters ("when the person shapes the item with a note"); `shall refuse the request and name X` |
| A sample value in a line | The group's given block, `shop work line --given` |
| A delivered line's text edited in `spec/` or on the item | `shop work line --retires <capability>#r<n>`: a new id, the old one retired |
| A new verb coined for a second operation of a word the person used (`browse` for "list all my checklists") | The person's word with a second entry and a frame that tells it apart, "list the checklists" (step 2) |
| A word added between two `shop work ready` runs | Every model line, relation and entry first, then the lines and one `shop work ready` |
| `shop spec parse --capability` | Gone: `shop spec parse` reads grammar 4 from `spec/index.md` |
| The person told to run `tools`, `work` or `migrate` themselves | The session runs them from `<scripts>` (A repository with no spec yet) |
| `spec/model/` or `spec/vocabulary/` written by hand for a first capability | `shop work line --capability`, then `--model`, `--relation` and `--term` on the item |
| A note, a rating's reason or a merge written into an item file by hand | `shop work annotate <b> "<text>"`; `shop work merge <b> --into <b2> --reason "<why>"`; `shop work ready` checks a ready item again |
| The person's words pasted into a note with no quote | `shop work quote` keeps the turns around them; cite quote-<n> (step 1) |
| Items shaped one after another though none needs another's result | One agent per item, in parallel, from `parallel-brief.md` (Shaping several items at once) |
