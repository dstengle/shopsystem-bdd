## How to work (standing rules, all from the person)

- **Keep the context small.** Agents reply in a few lines and leave the rest in files. Read files only to decide.
- **Use the plugin's roles:**
  - spec drafts: `capability-writer` / `initiative-round`;
  - scenarios: `feature-formulator` (blind);
  - code: `work run`, or `bdd-implementer` where `work run` cannot build itself;
  - reviews: `bdd-task-reviewer` / `bdd-branch-reviewer`;
  - term and consistency checks: `spec-checker`.

  Use a general-purpose agent only where no role fits, and say so.
- **Lines are strict EARS with "shall"**: the pattern follows what starts the behaviour, with one response per line.
  Use an If-line only where it is a check's purpose, protects files, or answers a failure that has been seen. Exits
  are worded "successfully" or "with an error". Each scenario names one requirement. Show proposed lines to the
  person in checked EARS (`model check` clean for v_e1/v_e2), never as prose.
- **Prove before specifying.** Gates are sized for sampling: one small gate page, recommendations marked.
- **Code and tests stay at 300 lines or fewer** (`tools size`). Markdown has no limit.
- **A refused tool action is reported, never achieved another way.** The coordinator lands feature files itself.
- **Commit often.** Push `release-0.23.0` after each green work-item and each gate:
  `agent-vault run -- git push origin release-0.23.0`. Run `work run` inside `agent-vault run --`, and commit
  `.shop/work/` before each run. Never push main or tag without the person's release approval.
- **No migration code.** Leave migration-tools as it is.
