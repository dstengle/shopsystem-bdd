Do not release yet. The suite and the checks are green, and the fault design is mostly built as its lines say.

out. The release also has no README section and the version is not bumped (R1, R2). Fix C1 and I1-I4 first. The rest
can go to the backlog.

## Critical

**C1. `work retry`, then `work run`, fails the work-item again, after a paid worker session.**
- **Where:** scripts/workqueue.py:164 (`retry` writes but does not commit), scripts/supervise_faults.py:62-84 (`checkout_changes`) and scripts/supervise_worker.py:152.
- **What:** `work retry w1` writes the status and log.jsonl and commits nothing. The next `work run i1` then starts a researcher. When it ends, r28 sees w1.md and log.jsonl differing from HEAD, puts them back (status `failed` again, the retry's log line dropped) and fails w1 with "changed in the repository's own checkout and not committed" (reproduced: /tmp/fr22repro/repro.py).
- **The same mechanism loses data:** `work add i1 w1`, then `work run i1` without a commit: the worker runs, `checkout_changes` deletes the untracked w1.md, and the run ends refusing "w1.md does not exist", leaving untracked log.jsonl and runs/ behind (repro2.py).
  - delivering-an-initiative commits its drafts and refuses a dirty checkout, so the skill's own path avoids this.
  - The README tells the person to run `work run` directly, and nothing teaches `work retry` + commit.
- **Why:** this is the one way out of `failed` (work-queue r8, decision 0056), and it does not work. work-queue r8 and supervision r28 act on one file without saying which wins (lesson 2). The ledger noted "work retry writes but does not commit" (line 19); the coordinator committed by hand (8f76b83).
- **Fix:** at the gate, choose one:
  - (a) `work run` refuses at start (r10) when `.shop/work/` differs from HEAD, naming the files;
  - (b) `work retry` commits its transition, which needs a line;
  - (c) `work run` commits what it finds at start.

  Separately, `checkout_changes` should never delete an untracked file it did not create; move it aside to `.shop/scratch/` and name it.

**I2. The branch review's findings are thrown away, and the review is not logged or checked.**
- **Where:** scripts/supervise_brief.py:54-76.
- **What:** `branch_review` writes its brief and result under the worktree's `.shop/scratch/branch-review/`, then `self.remove(tree)` (`--force`) deletes them. There is also:
  - no log.jsonl start/end line (r8);
  - no `cut_short` check (r45);
  - no output;
  - a new review on every `work run` of an initiative that is already all green.

  In plugin self-delivery, `self.outside` was already removed by `run()`'s `finally` (scripts/supervise.py:222), so the worktree's temporary directory is recreated and never removed (r33).
- **Why:** a paid opus session whose result is lost (lost data). Whether the branch reviewer is a "worker" is left to inference: the glossary says a worker is "for one stage of one work-item", yet ROLE lists it (lesson 2, reach).
- **Fix:** copy the reviewer's directory into `.shop/work/<i>/runs/branch-review/<k>/` and commit it, or give r27 a line saying where its findings go. Say in the glossary or r27 whether the branch reviewer is a worker.

**I3. A session that crashes is not a fault.**
- **Where:** scripts/supervise_faults.py:87-95 (`cut_short`).
- **What:** `cut_short` reads only the JSON on stdout. A `claude -p` that exits non-zero with non-JSON output (auth failure, crash, kill), having written its result first as `PARTIAL` (r44), goes to `awaiting-ruling` (r5) as a question for the person.
- **Why:** r45 says a session that "ends in an error" is `failed`. The stub never exercises this. Real turn-limit sessions in .shop/work/i8…/runs/*/1-research/session.json give `error_max_turns`, `is_error: true`, 26 turns, which the stub and the code do handle.
- **Fix:** treat a non-zero exit, or stdout with no JSON result, as cut short. Add a stub `exit` / `stdout` option and a row to the r45 outline.

**I4. Five i8 work-items were withdrawn by hand; `work run i8` now refuses.**

- **R3.** What a consuming repository must do to upgrade:
  1. Install 0.22.0.
  2. Split each scenario that names more than one requirement into one per requirement (`model check` v_s2), with steps shared in code.

  4. Give the initiative branch a pushable remote and run `work run` under push credentials.
  5. If `.shop/delivery.toml` sets `[tests] suite`, add `-p work_items --work-item {work_item} --whole-suite` to it, or lose r43's expected red.
