## Findings

**I1. Important, i18, fix now: `scripts/supervise_review.py:74`.**
- **What goes wrong:** if the push after the branch review's commit fails, `work run` crashes with a traceback. `scripts/work` only catches `Refused`, and this raises `Fault`.
- **Worse, the next run hides it:** it finds nothing unread and exits 0, so the review commit is never pushed (against r38).
- **Reproduced:** with a remote that accepts `--dry-run` but refuses the real push, run 1 gave the traceback and run 2 printed `w1 green` and exited 0.
- **Fix:**
  - Turn the failed push into a refusal that says why, as r51 does.
  - Push or refuse when the branch is ahead of its remote.
  - Add a scenario row for this case.

**I2. Important, i18, fix now: `scripts/supervise_faults.py:105` (`cut_short`).**
- **What goes wrong:** it checks the exit code before the JSON subtype. The real CLI exits 1 at its turn limit (i19's recorded faults say "exit code 1"), so a turn-limit session is now recorded as "session exited with an error (exit code 1)". That loses how the session ended, which r45 asks for and this release's turn-limit finding relied on.
- **Why the tests miss it:** the stub exits 0 on its turn-limit row.
- **Fix:**
  - Check `is_error`/`subtype` first, then fall back to the exit code.
  - Give the stub's turn-limit and error rows exit 1.

**I3. Important, i18/i19, release gate: work-item ids repeat across initiatives.**
- **What happened:** work-queue-1 exists in i10, i18 and i19; feature-file-tools-1 in i10 and i19; design-model-check-1 in i19 (the third v9b row).
- **Effects:**
  - `work retry` and `work withdraw` refuse these names as ambiguous.
  - According to the ledger, `--work-item` silently takes the first match.
  - i19's fft-1 and wq-1 stay `failed` and i18's wq-1 stays `drafted`, although their text says they were delivered.
- **Fix (person's decision):** make names unique, or let `work` take `<initiative>/<name>`. Then rename the three and set their statuses to what happened.
