### f3 Minor observation: `add` without `--checklist` refuses by naming a parameter, which no line asks for
- item: b1
- where: checklists.py:47
`kept()` refuses a missing `--checklist` with reason `no checklist`, names `parameter:checklist`, and prints the message `an item needs --checklist`. Line r6 only covers a checklist that does not exist, and says to name the checklist (`checklist:<title>`). Without this guard, the same request would be refused naming `checklist:None`, so the guard is reasonable hardening. Still, it is a refusal no line gives, and no scenario covers it.

Reproduction: `checklists.py add --text milk --json` returns `{"outcome": "refused", "errors": [{"reason": "no checklist", "names": ["parameter:checklist"]}], ...}`. If it should stay, add a line for it.

### f4 Minor observation: argparse errors skip the response envelope under `--json`
- item: -
- where: checklists.py:111
`check` takes `type=int`, and argparse handles bad arguments before `main` reaches its `try`. So `checklists.py check abc --json` prints argparse's usage error on stderr and exits 2. It returns no `{"outcome": "refused", ...}` object, and the exit code is not one of the 0/1 values in `spec/adapters/cli.toml`'s `[outcomes]`. No line names this input today.

### f5 Minor observation: the r7 scenario does not assert that the item ends `checked`
- item: -
- where: tests/scenarios/test_checklists.py:668
`keeps_item` only compares the kept item's text. A `check` handler that left the item `open` would still pass "Check an item off". That mistake is caught only indirectly, because the r8 scenario's setup checks an item and then expects a refusal. If `keeps_item` should hold the status too, it could compare against the status the request should leave.
