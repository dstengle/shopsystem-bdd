## Issues

### Important

1. scripts/features:452-467 (`binding_calls`, used by `unbound_report` at :509-512). Graded `spec question` and plan gap. Only `scenario()` calls whose title is a string literal count as bindings. Both step modules bind through `scenario(FEATURE, title)` with a variable title: tests/scenarios/test_feature_file_tools.py:69-77 and tests/scenarios/test_design_model_check.py:80-88, in `_bind(title)`, called from `for _title in BOUND`. As a result, `--unbound` reports all 116 of those bound scenarios as "bound by no test". r58 reads "bound by no `scenario(...)` or `scenarios(...)` call", and these are `scenario(...)` calls, so the report contradicts the line on the repository's own idiom.
   - Why it matters: every-scenario-bound (.shop/work/i11-final-layout/every-scenario-bound.md) requires this exact command to exit 0 for the three feature files. Its fileset is only tests/scripts/test_bound.py and tests/scripts/binding.py, so neither the tool nor the step modules can change there. As planned, the guard can never go green, and if it is forced green it guards nothing.
   - Fix, for the planner to choose:
     - (a) Here, teach `binding_calls` the repository's pattern: a title argument that is a parameter of the enclosing function, where that function is called in a `for <name> in <NAME>` loop over a top-level tuple or list of string literals, counts as one binding per element, at the element's line.
     - (b) Rewrite the step modules to bind with literal titles or with `scenarios(FEATURE)`, and add them to a fileset. `scenarios()` would also bind the scenarios BOUND deliberately leaves out, so it needs the planner's decision.
   - The scenario to formulate with the fix (r58): "Given features/cart.feature has the scenarios "Apply a code" and "Empty cart" / And a test module binding each title of a top-level tuple through a function that calls scenario("cart.feature", title) / When the agent runs features bindings --unbound / Then it says that every binding names a scenario / And it exits 0".

### Minor

1. scripts/features:494-505. `scenarios_calls(args.tests)` runs inside `for path, f in files`, so every test module is re-read and re-parsed once per feature file. `binding_calls` is then parsed a second time after `cmd_bindings` already parsed it (:533). Fix: call `scenarios_calls` once before the loop, and pass `cmd_bindings`' `binding_calls` result into `unbound_report`.
2. scripts/features:494-512. Graded `backlog`. pytest-bdd's `scenarios()` skips scenarios the calling module has already bound with `@scenario`. The tool counts both calls and reports "bound by m.py:3, m.py:9", although pytest-bdd binds the scenario once. Repro: one module with `@scenario("cart.feature", "Apply a code")` above `scenarios("cart.feature")`. No module in the repository does this today. Fix: when collecting, drop a scenarios() hit for a (file, title) that the same module already binds with a literal `scenario()`.
3. scripts/features:498-504. Graded `backlog`. A file argument matches by base name. `scenarios("sub/cart.feature")` binds features/cart.feature as well as features/sub/cart.feature, and one call that names both a directory and a file inside it is counted twice (`m.py:3, m.py:3`). Repro: features/cart.feature and features/sub/cart.feature, with one module calling `scenarios("sub/cart.feature")` and `--unbound`. The base-name match is consistent with the existing scenario() handling, so this is hardening only. Fix: resolve a path that contains a separator against --dir, and de-duplicate (module, line) per (file, title).
4. scripts/features:524. Graded `backlog`. `sorted(where)` sorts "module:line" strings as text, so within one module `m.py:12` sorts before `m.py:5`. Fix: sort by (module, int(line)).
