## Issues

### Important

1. scripts/model:321. v_e2 reports a line with no "shall". Line 321 has `one = len(shalls) == 1 and ...`, so zero shalls gives `one == False` and an `ears_many` fact. Probe: `[r1] \`thing\` answers when asked.` gives (False, False), so the line is reported under both v_e1 and v_e2. The same happens for every row of a table whose lead has no "shall". r104 is "more than one 'shall' or more than one sentence"; a line with none is v_e1's case alone. No scenario covers it: the v_e1 scenario never asserts v_e2, and the table-lead scenario at features/design-model-check.feature:616 checks only v_e1. This is a `spec question` only in that no scenario holds it; the line itself is clear. Fix: `one = len(shalls) <= 1 and not re.findall(...)`. Add `And v_e2 does not name r2` to the v_e1 scenario (r2 has no shall) so the fix is held.

2. scripts/model:332-334. An If clause ends the order check, so `If ... then` followed by another clause passes. ears() returns as soon as it sees `If`, without looking at what follows `then`. Probe: `**If** A, then **When** B, \`thing\` shall answer.` gives (True, True). So does `If A, then While B, ...`. r103 makes v_e1 "combines their clauses in an order other than Where, While, then When or If". When or While after If is such an order. Fix: after the If match, take the remainder after `then` as `rest`. Return False if it starts with a clause keyword (or keep looping with rank 3, which refuses it), and require a non-empty system before shall. Add a row to the v_e1 scenario's table, e.g. `| r7 | **If** asked, then **When** idle, \`thing\` shall answer. |`, under "v_e1 names".

### Minor

3. scripts/model:253 and 257 (`backlog`). The table lead is stale or borrowed. `lead` is set by every bullet, an id'd requirement included, and is never cleared by a `###` heading or by the end of a table. Probes:
   - `- [r1] **When** asked, \`thing\` shall answer.` then a table `| [r2] | two |`: r2 is checked against r1's text and passes.
   - A second table under a new `###` with no lead inherits the first table's lead.

   The report's ruling 3 ("a table with no lead sentence reports every row v_e1") holds only when nothing at all precedes the table. Fix: reset `lead = None` on a `#` line and after a table ends, and make a lead only from a non-id bullet ending ':' or a paragraph.

4. scripts/model:246 (`backlog`). A table row whose id lost its brackets (`| r1 | one |`) is dropped silently. It is neither a requirement nor a v15a nor a file problem. Probe: behaviour_items returns nothing for it. Fix: report a row whose first cell matches `r\d+` without brackets under v15a or as a file problem.

5. scripts/model:321 (`backlog`). The sentence count treats an abbreviation as a sentence end. `\`thing\` shall answer, e.g. with a value.` gives one == False, so it is v_e2. Fix: ignore `e.g.`, `i.e.`, `etc.` before counting, or accept and document it in docs/capability-format.md.

6. scripts/model:316-345 (`backlog`). Some non-EARS lines pass as ubiquitous. The matcher accepts any non-empty text before "shall" that does not begin with a capitalised keyword:
   - `Sometimes \`thing\` shall answer.` gives True.
   - `when asked, \`thing\` shall answer.` (lower-case when) gives True.
   - `Each row below shall be reported.` gives True.

   0051 requires the system to be named; the matcher cannot check that, and r103 does not ask it to. Fix (optional): match the clause keywords case-insensitively at the line start. Otherwise leave system-naming to the spec-checker's judgement.

7. features/design-model-check.feature:616. The scenario promises more than the check does. Its Given says the lead "names no system", but the fixture lead ("Each row below is reported.") fails for having no "shall". A lead that names no system but has a shall (`Each row below shall be reported.`) passes (finding 6). Fix: reword the Given to "led by a sentence with no shall", or make the matcher check system naming.

8. docs/capability-format.md:305-307. The Checking section still teaches v_s2, contrary to 0052. It says model check reports "a scenario that names no line or two (`v_s1`, `v_s2`)" and does not list v_e1/v_e2. This is in the fileset, and the rule is gone. Fix: "a scenario that names no line (`v_s1`)", and add "a line not in an EARS pattern, or with more than one shall or sentence (`v_e1`, `v_e2`)".

9. docs/capability-format.md:110-112. 0051's "message wording and minor refusals belong in Implementation, may change" is carried only as "the words of a message ... are implementation". Minor refusals are not mentioned. Fix: add "and minor refusals" to that sentence.
