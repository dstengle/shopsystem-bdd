**On your first question, yes.** Every part of laying is a specification tool aimed at a different folder, and the folder being a branch only matters for the commit at the end.
- **lay** does the same writing as `work ready` and `spec check --item`: the `backlog_*` lay functions (`backlog_lines.lay_onto`) putting the item's lines into a spec. The readiness bar points them at a throwaway copy of `spec/`; the batch points them at the batch branch's worktree. Three steps exist only for the batch:
  - it renumbers the item's ids past the capability's;
  - it adds the new ids to `unbuilt:`;
  - it commits the result.

  The renumbering already happens on the readiness copy too, and `unbuilt:` is a specification field. So these are specification concerns as well.
- **prepare** runs `features generate`, `spec rules --write`, `spec constructs --write`, the corpus write, the `## Composition` rewrite, `spec annotate` and the decision-successor write, all with that worktree as the root.
- **check** is `spec check`'s error-level rules on that root, minus whatever was already broken before the lay.

So there is really one specification operation: "this specification at this root, with this item's lines in it." It is used in three places today (`work ready`, `spec check --item`, `work batch start`), and only the last goes through the laying port.

**Not as far as the spec is concerned.** The pick already requires each item to pass the readiness bar on its own, against `main`, as well as laid over the items picked before it. An item that fails alone goes back to `shaped`. So no task needs another task's lines in order to parse, generate scenarios or be checked. Giving every task branch every item's lines is what creates the problem the lift exists to fix.

**Numbering isn't the issue.** The pick renumbers ids once, across the whole pick: each item's new ids come after its capability's ids and after the items picked before it, and they're written onto the item. If each task laid only its own item's lines, the ids would still never collide and every reference would still resolve.

**The real issues, and how each could be handled:**
1. **Shared files conflict when the tasks merge.** Two items in one capability both append groups to the end of its `## Behaviour`, both add ids to its `unbuilt:` line, and both rewrite its generated feature. They also both touch the corpus, the catalogues, `## Composition`, and the model and vocabulary files of the same area. Git merges of those collide. Today `batch_merge` already special-cases the `unbuilt:` conflict for this reason.
   - **Fix:** never merge spec files with git. At review, lay the surviving items onto the base again and prepare the spec there, then merge only the tasks' code and tests. The spec on the batch branch is then always "the base plus the items still in the batch", rebuilt from scratch, and a parked item simply isn't among them.
