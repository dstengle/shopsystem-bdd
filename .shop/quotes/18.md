Yes, mechanically. The entailment check records which premise each consequence comes from (U11, plus the pack's definition of "refuse"). So any tool can print the expansion next to the line, always in step with the definitions. The CNL literature calls this a *paraphrase back to the writer*; Attempto does it for every sentence. There are three places to show it:

**1. In the generated Gherkin, always.** The scenario spells everything out, marking where each step comes from:

```gherkin
@r12
Scenario: work ready refuses an item whose lines do not parse
  Given an item i1 with a requirement line that does not parse
  When the person runs `work ready` on the item i1
  Then `work` refuses the command
  And `work` names the requirement line
  # from U11 (refuse, CLI pack):
  And `work` exits with an error
  And `work` changes nothing
```

The entailed steps can stay as real steps, so they're tested, or become comments if the universal check after each scenario already covers them. Either way, a reader of the feature file sees the whole behaviour.

**2. An explain command for one line**, e.g. `model explain readiness#r12`:

```
readiness#r12: If the person runs `work ready` on an item whose lines do not parse,
  then `work` shall refuse the command and name the line.
  which also means:
    `work` shall exit with an error naming a reason   (U11)
    `work` shall change nothing                        (U11)
  where "refuse": a tool refuses a command when it exits with an error on it   (CLI pack)
```

The authoring and review skills could show the same, so a writer sees what a line commits to before readying it.

**3. In a rendered view of the spec**, such as a capability page where "refuse" links to its definition and the line can be expanded in place.

I would keep the capability file itself as the short form. Writing the expansion into the source would duplicate what the definitions already say, and the copies could drift apart.
