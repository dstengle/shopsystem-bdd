```text
I'll check what the request skills say about starting the watch.

It isn't fully automatic: nothing starts it on its own. It's a command, `work watch` (from b31 "A session watches its request issues and wakes on a new comment"), and the request skills tell the session to start it.

**What it does:**
- It polls GitHub every 60 seconds (`--every` changes this). It checks the issue of each request that isn't closed, and this repository's own open issues for new asks.
- When the other side posts a comment the request doesn't hold yet, or a new ask arrives, it prints one line for each and exits.
- It writes nothing itself. It keeps only a small note in the git directory, so it doesn't wake on the same comment twice.
- A failed GitHub call is printed and the poll is tried again; it doesn't end the watch.

**How it starts:** a skill tells the session to start it in the background, with Bash's background mode or the Monitor tool. Three skills do:
- **raising-a-request**, step 8: while a request this repository asked waits on the upstream.
- **taking-in-a-request**, step 7: while a request waits on the asker, or a new ask may come.
- **building-a-batch**, step 1: while any request waits on the other side.

When the watch exits, the session wakes up and runs `work sync` to record the comment. It then takes that request's next step and starts the watch again, until no request waits on the other side.

**What that means in practice:**
- It runs only while a Claude Code session is open and has followed one of those skills. Nothing starts it when a session opens: the start-of-session hook only checks the plugin version and lists the items' names.
- If the session ends or is compacted mid-watch, the watch stops. The next session restarts it only if it happens to run one of those skills.
- No session in this repository has started it yet, because no request has been waiting on the other side.
```

```text
I'll load the Monitor tool's description to see what it reacts to.

Yes, GitHub can push issue events, through webhooks, but not directly to a terminal on this machine. The Monitor tool is event-driven only on the session's side, so something still has to deliver GitHub's events to it.

**How Monitor works:** it runs a command, or opens a WebSocket, and each line the command prints (or each message the socket receives) wakes the session as a notification. It doesn't connect to GitHub itself. A Monitor that runs a polling loop is still polling; it just reports each find without the session waiting. Each Monitor also ends after at most 30 minutes, so a long watch has to be restarted.

**What GitHub offers:**
- **Webhooks (push):** GitHub sends an HTTP request for each issue opened and each comment posted, within seconds. It needs a public HTTPS address to send to, and admin rights on the repository to set one up. This is the only push option.
- **`gh webhook forward` (push, to this machine):** an extension for `gh` (`gh extension install cli/gh-webhook`, not installed here). GitHub holds the connection open and forwards the repository's webhook events to a local port, so no public address is needed. A small listener on that port prints one line per event, and Monitor turns each line into a wake-up. It needs admin rights on the repository and is a preview feature meant for development.
- **Notifications API (polling, cheaper):** still polling, but cheap. I checked it here: GitHub asks clients to poll it no more than every 60 seconds (`X-Poll-Interval: 60`). A poll that finds nothing new returns "not modified" and doesn't count against the rate limit. It covers every repository the account watches in one call, not one call per issue.
- **GitHub Actions:** a workflow can run on each comment, but it runs on GitHub's servers and can't wake a session here.
```
