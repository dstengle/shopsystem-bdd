**1. Why the CLI driver: you're right, and it's a gap in the current design rather than a requirement of b418.**

When I said "the binding creates it through the CLI adapter", I was describing today's wiring. The domain-contract design (§6.2) follows Farley's layers: generated scenario → step definitions → handlers keyed on the operation (`WhenRequests checklists.create`) → a **protocol driver**. The only driver built so far is `driver_cli.py`. It turns the operation into argv using `cli.toml`, runs the command, and reads the envelope back. So the scenarios do name core operations, but they reach the core through the port.

What you're describing is a **core driver**:
- It calls the service's operations in process, by their model names, and gets the same `Response` envelope back.
