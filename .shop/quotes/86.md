I don't think it's worth splitting them now. Part of the walk-through is worth doing anyway; the rest is more machinery than the problem needs.

**The main test is language, and it says they're one context.** A bounded context is drawn where a word starts to mean something different. In this repository an "item" means the same thing to tracking and to execution: the same statuses, lines and id. Execution doesn't need a different model of an item. "Assignment" was a new word made up to fit a split, not a word anyone already uses, and needing one is usually a sign the boundary is artificial.

**What a split would cost:**
- a port, an adapter, and four new operations;
- a new word, with execution's 68 lines reworded into it;
- a second contract to publish and keep versioned;
- conformance tests across the boundary.

All of this inside one shop, one command (decision 0132), one `.shop/` store and one team. Nothing on the other side of the port could be swapped out today.

**What's actually wrong, and worth fixing regardless:** execution changes item and request statuses directly. 10 of its lines set them, and its code makes 35 imports into tracking. Four of an item's status changes (into a batch, delivered, back to ready, needs input) have no tracking operation behind them at all. That's a missing boundary inside one context, not a missing context. The fix is to give tracking those four operations and have execution call them rather than write item files. In DDD terms these are two modules of one work-management context, with the item's lifecycle owned by one of them.

**When a split would pay off:** if execution had to work from a tracker that isn't this one, such as GitHub Projects, Jira or another team's backlog, or if tracking had to feed an executor other than batches. That is exactly the case where provider swaps and brownfield adoption matter, and the walk-through shows how to do it when it comes. Doing the four operations first makes that later split cheap.
