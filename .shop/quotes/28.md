Let me map every place a version number lives before proposing anything:

It's mostly mechanical, with one decision first: where the new 0.y series starts. The plugin was already a 0.x series once. Releases 0.1 through 0.29 were tagged (`v0.1.0` … `v0.29.0`), and repositories recorded those numbers before the jump to 1.0.0. So a reset can't restart at 0.1.0 without colliding with that history and confusing `migrate`, which orders versions numerically.

**My recommendation: continue the old series from 0.30.0** and renumber the five majors as the minor releases they really were:

| Released as | Becomes | What it was |
|---|---|---|
| 1.0.0 | 0.30.0 | codified requirements |
| 2.0.0 | 0.31.0 | the workflow simplified |
| 3.0.0 / 3.0.1 | 0.32.0 / 0.32.1 | verb frames |
| 4.0.0 | 0.33.0 | the controlled language 4 |
| 4.1.0 | 0.34.0 | value kinds |
| next (the Given fix, #51) | 0.34.1 | non-breaking fix |

That keeps every version in true order, so a repository recorded at 0.29 still upgrades correctly.

**What the reset touches:**
1. **The version itself:** `.claude-plugin/plugin.json` and this repository's `.shop/plugin-version` go to 0.34.1.
2. **`migrate`:**
   - its upgrade steps are keyed by version (`1.0.0` … `4.1.0`) and get renumbered;
   - a repository that recorded an old number (feed records 3.0.1) needs that number translated once. That's a small table in `migrate`, or a one-time rewrite of its `.shop/plugin-version`. Without it, `migrate status` would say feed is *ahead* of the plugin.
3. **The spec:** migration-tools names releases in its values, lines and example data (about 40 places). Those lines get reworded with new ids.
4. **The docs:** the CHANGELOG headings, upgrading.md, getting-started and the commands reference. The CHANGELOG would keep each old number in brackets ("0.33.0, released as 4.0.0") so history stays readable.
5. **Not touched:** records and backlog notes. They're history, never edited, and say 4.0.0 because that's what happened.
