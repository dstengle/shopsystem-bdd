## 1. What an actor can do with a domain

Three kinds of interaction:

| Interaction | The actor… | Possible answers |
|---|---|---|
| **Command** | asks the domain to change something: enter a decision, accept a request, start a batch | done (with what changed), or refused with the reasons |
| **Query** | asks what is so: show an item, list the backlog, check the spec | returned content, which may be findings |
| **Notification** | is told something happened, without asking: `work watch`, the session-start hooks | the event and its content |

A fourth answer is outside the domain: a **failure**, where infrastructure broke (git, the disk, a crash). It is not a refusal. b3's note already settled that the CLI shows both as exit 1, but the business contract should keep them apart.

So a line would use a domain verb with the request's data attached:

> When the person enters a design-decision with the tier `check`, `work` shall record the design-decision.
> If the person enters a design-decision without a tier, then `work` shall refuse the request and name the tier.

The pack gives only the request side: the request, its parameters ("with the tier …"), refuse, return and notify. The domain supplies the verbs. This differs from variant A, the earlier version that moved inputs onto domain things: there the parameters became facts about the design-decision and the request disappeared. Here they stay attached to the act.

The cost is in the grammar. Today only `run` can take options, and that is hardcoded in about seven modules. Under this design, any action verb that is an operation would take parameters, and refuse and return would apply to any request. That is the main change to the plugin.
