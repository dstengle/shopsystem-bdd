Yes, GitHub can push issue events, through webhooks, but not directly to a terminal on this machine. The Monitor tool is event-driven only on the session's side, so something still has to deliver GitHub's events to it.

**How Monitor works:** it runs a command, or opens a WebSocket, and each line the command prints (or each message the socket receives) wakes the session as a notification. It doesn't connect to GitHub itself. A Monitor that runs a polling loop is still polling; it just reports each find without the session waiting. Each Monitor also ends after at most 30 minutes, so a long watch has to be restarted.

**What GitHub offers:**
- **Webhooks (push):** GitHub sends an HTTP request for each issue opened and each comment posted, within seconds. It needs a public HTTPS address to send to, and admin rights on the repository to set one up. This is the only push option.
- **`gh webhook forward` (push, to this machine):** an extension for `gh` (`gh extension install cli/gh-webhook`, not installed here). GitHub holds the connection open and forwards the repository's webhook events to a local port, so no public address is needed. A small listener on that port prints one line per event, and Monitor turns each line into a wake-up. It needs admin rights on the repository and is a preview feature meant for development.
- **Notifications API (polling, cheaper):** still polling, but cheap. I checked it here: GitHub asks clients to poll it no more than every 60 seconds (`X-Poll-Interval: 60`). A poll that finds nothing new returns "not modified" and doesn't count against the rate limit. It covers every repository the account watches in one call, not one call per issue.
- **GitHub Actions:** a workflow can run on each comment, but it runs on GitHub's servers and can't wake a session here.
