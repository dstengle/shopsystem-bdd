### the session, 2026-11-11T03:19:23.129000+00:00, 4d41a84d-9e1f-49c2-be78-578a3e05f5c4

````text
Let me confirm the explicit form parses as well, so I can show both:

Yes, it parses, to exactly one reading. `` `idea` `` isn't an adjective; it's one of the declared values of an item's **status**. The glossary declares it in `spec/index.md`:

```
- **status** (attribute of item): Values: `idea`, `shaped`, `ready`, `in-batch`, `delivered`, `needs-input`, `refused`, `withdrawn`.
```

So "an item is `idea`" is short for "the status of an item is `idea`". The grammar can fill in the attribute because `idea` belongs to only one attribute of an item. The backquotes mark it as a value rather than a word. `model parse --form` shows what the line means:

```
shall [x2: agent the person (constant), x3: command `work shape` (parameter), x4: tool `work` (constant)]
  while [x1: item]
    status(x1) = `idea`
  when
    run(e1, subject: x2, object: x3, on: x1)
  response
    initiates(e2, subject: x4, status(x1) = `shaped`)
```

The explicit form, "While the status of an item is `idea`, …", also parses, to the identical meaning.

The short form stops being allowed in two cases:
- **Ambiguity:** if an item had two attributes that both allowed `idea`, the short form would read two ways and be refused. You'd then have to name the attribute.
- **Undeclared values:** a value no attribute declares is refused too, so you can't slip a coined word in as a value.

The README doesn't explain any of this, and a reader meeting the line cold has no way to know `idea` is a declared value. I'd add one sentence under the example, along the lines of "`` `idea` `` and `` `shaped` `` are values of an item's status, declared in the glossary", with a link to where writing-requirements explains values. Should I make that change?
````

### the session, 2026-11-11T03:25:53.882000+00:00, d4314ed6-cbc2-471f-81d5-5ae6363b7899

```text
You're right. The short form reads well only when the value is something you can *be*: "an item is `shaped`", "a request is `accepted`", "a batch is `building`". With a noun it's broken English: "an item is `idea`". It isn't only `idea` either. Several values across this spec aren't adjectives:

| Attribute | Values that read badly in "X is `v`" |
|---|---|
| item status | `idea` (noun), `needs-input` (verb phrase) |
| design-decision tier | `check`, `requirement`, `judgement` ("a design-decision is `check`") |
| repository release | `own`, `1.0.0` ("a repository is `0.23.1`") |

`in-batch`, `in-review` and `awaiting-merge` are borderline but acceptable.

So the grammar's shortcut lets a line be grammatical to the parser but not good English, which goes against the language's own aim. Three ways to fix it:

1. **Only adjective-like values may use the short form.** Each attribute declares which kind its values are, e.g. `Values (adjective): shaped, ready, delivered` versus `Values (noun): check, requirement, judgement`. Noun values must use the full form: "an item whose status is `idea`", "the tier of the design-decision is `check`". The parser enforces it, and lines like the README's get reworded.
2. **Rename the values** to adjectives or participles (`idea` to `proposed`, `needs-input` to `waiting`, and so on). The short form then always reads naturally. But these are user-facing state names, used by `work idea`, `work backlog` and the docs, and tiers and versions have no adjective form anyway.
3. **Drop the short form** and always write "whose status is" or "the status of X is". It's always good English, but adds about three words to many lines that read fine today.

My recommendation is 1. It keeps the natural short form where it works ("an item is `shaped`"). Where it doesn't, it requires the full form, which is good English in every case. And it's a rule the parser checks, not a style note.
```
