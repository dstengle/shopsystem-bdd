### the session, 2026-11-05T18:45:15.395000+00:00, 511c5fc8-9c37-4663-b77c-c1d9671a621d

```text
Right, `work` no longer runs `claude -p` agents. Plugin 2.0 retired `work run`, which supervised `claude -p` sessions through the queue stage by stage (research, plan, implement, review, gate). Decision 0074 "The workflow simplified" replaced it and superseded "a script supervises delivery". In 2.0, `work batch` only keeps state on disk and runs the checks. The session building the batch dispatches the agents itself, as the building-a-batch skill says.

The 2.0 decision gives two reasons:
- **Speed:** under `work run`, initiatives sat open 18–119 hours waiting on question gates, for 15–104 minutes of actual session time.
- **Cost:** reviewing every task was the largest single cost and found little to fix. The GF conversion, built in-session with superpowers' process, cost about a tenth of the estimate for doing it with `work run`.

So now one fresh agent builds each task, one review happens at the pull request, and a task that hits a question gets parked instead of waiting.

As for "general-purpose": the plugin ships no implementer agent type. It has only `pr-reviewer`, `architecture-reviewer` and `trial-runner`. The skill tells the session to dispatch "one subagent for each running task" without naming a type, so I used `general-purpose` with the skill's brief. The review step does use the dedicated `pr-reviewer`, given only its brief.

If you want the builders pinned down the same way, a `batch-implementer` agent type is a reasonable addition. It would fix its tools, model and rules (red first, `Item:` trailers, no `.shop/` edits) in its definition instead of in each brief. I can add that as a backlog idea; the running task isn't affected either way.
```
