# Tracking owns the item's lifecycle and execution changes it through tracking's operations

## Notes

quote-86, decision 0133: tracking gains the operations for the item's changes into a batch, delivered, back to ready and needs-input (allocate, discharge, restore, suspend), and execution's lines and code request them instead of setting an item's or a request's status or writing its file.
Decision 0133: tracking owns the item's lifecycle; execution changes it only through tracking's operations (quote-86). The backlog service gains allocate (ready → in-batch: the item is given to a batch's work), deliver (in-batch → delivered: the item's change is in the product), restore (in-batch → ready: the item goes back to wait for a batch) and suspend (in-batch → needs-input: the item waits on an answer, with its question). Names chosen as the business acts on the item: deliver matches its status delivered; allocate, restore and suspend say what happens to the work, not how. Execution's lines that set an item's or a context request's status are retired by lines in which the batches service requests these operations (and backlog.reopen, context requests.resolve, which exist).

## Requirements

### tracking model

```model
service backlog
  operation allocate(item)  outcomes: done
  operation deliver(item)  outcomes: done
  operation restore(item)  outcomes: done
  operation suspend(item, question)  outcomes: done
```

- **allocate** (verb, action) → operation backlog.allocate. Forms: allocates, allocated. Frame: <actor> allocates <item>.
- **deliver** (verb, action) → operation backlog.deliver. Forms: delivers, delivered. Frame: <actor> delivers <item>.
