# A reply trigger is said after fail too

## Notes

batch-127 b626: the request pack's fail takes a check, not a request, so 'fails the request to V <np>' does not parse, while the replied request's vocabulary entry says complete, return, refuse or fail. Give fail a frame on a request, or take 'or fail' out of the entry.
The replied request's vocabulary entry says the reply trigger follows complete, return, refuse or fail, but the request pack's fail takes a check (service fails check), so 'the registry fails the request to publish a design-decision' does not parse. Technical call: fail is given a request, not the entry reworded: a failure is a reply the domain envelope already has (the outcome failed), and an item has no way to restate a delivered vocabulary entry (backlog_model's lay only appends terms). The request pack's fail gets the frame 'service fails request' beside its check frame, spec_rgl_ops' reply trigger is generated after fail too, and the construct catalogue gets the entry reply-failure (its form '<service> fails the request to <operation verb> <np>', its example in the request context). World that fails first: a row of design_model_check_worlds in the construct catalogue's request context whose r1 is the text 'When the registry fails the request to publish a design-decision, the decisions service shall keep the design-decision.' written in the world (not read off the catalogue, which has no reply-failure entry before the fix); today it does not parse, since fail takes a check.
