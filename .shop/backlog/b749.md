# A feature generator run that times out or cannot start is a refusal of work batch start, park and amend, not a crash

## Notes

batch-135 review 1 observation: batch_generator._run's subprocess TimeoutExpired/OSError escapes batch_start._generated, which only catches GenerateError; generate_all skips its per-capability fallback.
Fix: batch_generator._run catches subprocess.TimeoutExpired and OSError and raises features_generate.GenerateError naming the feature generator and why (timed out after <n> s / could not start: <err>), so batch_start._generated's refusal covers start, park (unlay) and amend; generate_all treats such a first run as failed and falls back per capability. Technical call: the time limit is read from $SHOPSYSTEM_GENERATE_TIMEOUT (seconds, default 600) so a scenario can stall a generator cheaply. World to fail first (extend tests/scenarios/batches_handlers_generator.py, r170's world): the batch's workspace holds scripts/features that sleeps 30 s, committed; the scenario sets $SHOPSYSTEM_GENERATE_TIMEOUT=1; today amend/park crash with a traceback (exit not a refusal, branch state left), so 'refuse the request, name the feature generator and change nothing' fails until the fix. start shares the code path (its tree's generator is the base's) and is covered by the same fix, no scenario. Source: batch-135 review 1 observation.
Rated medium value (a crash leaves a batch half-laid), medium urgency (only a stalled generator triggers it), small size (a try/except, an env var, one world).
