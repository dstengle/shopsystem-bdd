# The product's domain map: subdomains and the bounded contexts that address them

## Notes

Decisions 0128, 0141, 0143. The domain map of the product: subdomains with their type (core, supporting, generic) and the jobs they serve; the bounded contexts with the subdomains each addresses and the shop that hosts it, or none for a third-party provider (0143); each job assigned to one bounded context (a reassignment keeps the earlier one as history); per bounded context the term (an actor of its model) that plays each product actor (0141). Technical calls: operations of the product service (b602), CLI spec subdomain, spec context, spec assign, spec plays. Needs b602's product and jobs and b576's hosted contexts.
Rated: high value (the domain map replaces areas' subdomain kinds, b615), medium urgency, medium size (about seven lines: subdomain, context entry, assignment, actor mapping and their refusals). Lines in the product capability once b602 is delivered.
Split (size): job assignments and the actor mapping went to b675. Lines product#r8-r14 (renumbered past b673's and b674's when laid). Technical calls: operations product.declare subdomain (spec subdomain <id> --type --serves) and product.declare context (spec context <id> --addresses --shop), kept in the product layer beside its jobs (product_store; b673 keeps the other keys); a subdomain's type is a subdomain type of the subdomain type form (core, supporting, generic), not an attribute, since 'the subdomain type' read two ways; a context's id lies under the product's id (cover, as the shop's keep checks the product id); a context with no --shop is a third-party provider (0143). How the worlds must be built so each scenario fails before: product_handlers writes the product file with the product's id (example.org) and the jobs and subdomains the Givens say are held, runs spec subdomain or spec context with the instance values (a subdomain type t1  unless a Given says it does not conform, then ; an id i1 under example.org unless the Given says the product's id does not cover it, then other.org/i1; a job or subdomain held unless a Given says not); the keep Thens read the subdomain or context back from the kept product file (with its type and jobs, or its subdomains and shop, none for a provider); the refusals check an error exit, nothing committed and the option named. Before the fix spec subdomain and spec context do not exist, so every scenario fails.
Correction of the note above (a shell ate its codes): a subdomain type t1 is `core` unless a Given says it does not conform to the subdomain type form, then `central`.

## Requirements

### product

#### [g15] A subdomain is declared with its id, type and jobs
- [r15] When the person declares a subdomain with an id and a subdomain type and a job, the product service shall keep the subdomain in the product and complete the request.

#### [g16] A subdomain of a type outside the subdomain type form is refused
- [r16] If the person declares a subdomain with a subdomain type that does not conform to the subdomain type form, then the product service shall refuse the request and name the subdomain type.

#### [g17] A subdomain serving a job the product does not hold is refused
- [r17] If the person declares a subdomain with a job that is not in the product, then the product service shall refuse the request and name the job.

#### [g18] A bounded context a shop keeps is declared in the domain map
- [r18] When the person declares a bounded context with an id and a subdomain and a shop, the product service shall keep the bounded context in the product and complete the request.

#### [g19] A third-party provider is declared as a bounded context no shop keeps
- [r19] When the person declares a bounded context with an id and a subdomain and without a shop, the product service shall keep the bounded context in the product and complete the request.

#### [g20] A bounded context whose id lies outside the product is refused
- [r20] If the person declares a bounded context with an id that the id of this product does not cover, then the product service shall refuse the request and name the id.

#### [g21] A bounded context addressing a subdomain the product does not hold is refused
- [r21] If the person declares a bounded context with a subdomain that is not in the product, then the product service shall refuse the request and name the subdomain.

### specification model

```model
object product
  relations: holds → subdomain | bounded context (many)

object subdomain
  relations: has → id (one); has → subdomain type (one); serves → job (many)

object bounded context
  relations: addresses → subdomain (many); is hosted by → shop (one)

object id
  relations: covers → id (many)

service product
  operation declare subdomain(subdomain, id, subdomain type, job)  outcomes: done → the subdomain | refused: subdomain type not in the subdomain type form, job outside the product
  operation declare context(bounded context, id, subdomain, shop)  outcomes: done → the bounded context | refused: id outside the product, subdomain outside the product

object subdomain type kind of text

object subdomain type form kind of artifact
```

- **subdomain** (noun) → object subdomain. A part of the product's problem that the product declares with its id, its type and the jobs it serves, which bounded contexts address (decision 0128). Plural: subdomains.
- **declare** (verb, action) → operation product.declare subdomain. The person writes a subdomain of the product with its id, its type and the jobs it serves. Forms: declares, declared. Frame: <actor> declares <subdomain>.
- **declare** (verb, action) → operation product.declare context. The person writes a bounded context of the product's domain map with its id, the subdomains it addresses and the shop that keeps it, or none for a third-party provider (decision 0143). Forms: declares, declared. Frame: <actor> declares <bounded context>.
- **cover** (verb, state) → relation id.covers. An id lies under another: its path opens with the other id. Forms: covers, covered. Frame: <id> covers <id>.
- **subdomain type** (noun) → object subdomain type. How the product weighs a subdomain, as `core`. Plural: subdomain types.
- **the subdomain type form** (proper noun) → object subdomain type form. `core`, `supporting` or `generic`, the types of subdomain decision 0128 names.
