# work line --remove reads which id a line retires from the item, not commit subjects

## Notes

batch-39 review 1 observation (b14): backlog_reword._retiring reads the newest 'work line: ... retires ...' commit subject, so an id reused within one item can clear the wrong retired id; keep which line retires which id in the item's block.
Seen by the release 0.35.2 review (2026-11-16): on a clone, a line written with --retires backlog#r41 then --remove'd, then --retires backlog#r41 --no-line, then a plain line that got the reused id r44, then --remove backlog#r44: retired: lost r41. The history search of '<id> retires' matches the old line of the same id.
Shaping (2026-11-16): a defect of delivered b14. Reproduced on a throwaway clone (scratch b323repro, item b341): `work line b341 --into backlog --retires backlog#r41 "<line>"` wrote r45; `--remove backlog#r45`; `--retires backlog#r41 --no-line`; a plain `--group plain "<line>"` got the reused id r45; `--remove backlog#r45` then printed `backlog#r45 removed` and left `## Requirements` empty: `retired: [r41]` was lost, because `backlog_reword._retiring` matched the old commit subject `... backlog#r45 retires backlog#r41`. Fix: which line retires which id is kept in the item's block, never read off git history. `work line --retires` (scripts/backlog_retires.py, `with_retired`) writes the pair into the block (a block line beside `retired:`, e.g. `retires: [r45 r41]`, its exact form the plan's), `scripts/backlog_section.py` reads and renders it byte-stable and ignores it when laying (`backlog_retires.lay` still lays only `retired:`), `scripts/backlog_reword.py` drops `_retiring` and removes only the id its pair names (and drops the pair), `--reword` keeps the pair, and `backlog_lines.renumber` renumbers the pair's line id with the line (never the retired id, a live capability's). `--no-line` writes no pair, so its id survives any `--remove`. No compatibility for items written before (alpha): an item with a `--retires` line and no pair keeps its `retired:` on `--remove`. Scenario of r51: an item holds a requirement r1 and a requirement id that r1 does not retire (as `--no-line` writes it); `work line --remove` of r1 leaves that id under `retired:`; its counter-example the id r1 retires, removed. Handlers in tests/scenarios/readiness_handlers_line.py and readiness_handlers_thens.py; the term retire (state sense, requirement retires requirement id) added to readiness. Left out: a positive line that removing a `--retires` line removes its retired id (b14's note says it, no delivered line does; r51's counter-example covers it). No quote: filed after the 2026-11-16 triage, from the batch-39 review and the 0.35.2 release review.

## Requirements

### readiness

- **retire** (verb, state): a requirement an item holds takes the place of the live requirement whose requirement id the item holds, as `work line --retires` writes them. Forms: retires, retired. Frame: requirement retires requirement id.

#### [g51] `work line --remove` keeps a requirement id the removed requirement does not retire
- [r51] When the person runs `work line` with the `--remove` option set to the requirement id of a requirement in an item on the item, `work` shall not remove a requirement id in the item that the requirement does not retire.
