# Reword migration-tools r77, r78 and r79 with value-compare and value-same over the term release

## Notes

b275 added the constructs and the term release but retired nothing; grammar/language.md says the lines keep their plain wording until a reword item retires them (batch-35 review 1).
Retires migration-tools r77, r78, r79 for r81 (value-same), r82 (value-compare) and r83 (value-same), each saying the repository's release against the release of `migrate` (the version in the plugin's .claude-plugin/plugin.json), so no line or given block names the plugin's own release and none needs editing at 0.35.0; r80 is untouched. The groups' given blocks no longer write .shop/plugin-version (g81 and g82 have none; g83 keeps only the initiative file i1): features generate gives each side a value that meets the comparison (on a copy of spec/ it wrote 'the release of this repository is `0.23.1`' and 'the release of `migrate` is `0.23.1`', and `0.23.0` for r82's migrate), so the handler must make both real: the Given of the repository's release writes the scenario repository's .shop/plugin-version with its value, and the Given of the release of `migrate` runs migrate (and the SessionStart hook) from a copy of the plugin's scripts and hooks whose .claude-plugin/plugin.json says that value (migration_old.plugin generalised from its one TARGET to any version), never from the real plugin.json; migration_tools_handlers.recorded's check that 'this repository is v' matches the given block's plugin-version goes. Blocked: the lines parse only when release is one attribute of both kinds; the spec has 'release (attribute of repository)' and b275's separate 'release (attribute of tool)', and value-compare and value-same take one attribute's noun phrase on both sides, so 'the release of `migrate`' does not parse after 'the release of this repository is after'. On a copy of spec/ with the two entries merged into 'release (attribute of repository, tool)' (the repository's values, Order: by number) all three lines parse to cmp(release(x1), same|after, release(x2)) and features generate writes them; a third entry appended by work line --term instead brings v_t2 and v_t5. No work command edits or removes a term entry, so the merge needs b275's term fixed in spec/ (a defect of b275, whose language.md #6 says this form parses) or a build of this item that rewrites the entry before work ready can pass.
