# 'every K in the Y, ordered by T' after a verb whose frame names K reads one way again

## Notes

Fix of batch-40's defect of b300 (the defect record under .shop/batches/40/): 'every K in the Y, ordered by T' after a verb whose frame names K reads two ways since b300 and is refused, where 0.35.1 read it one way. A line that parsed must parse to the same one meaning: either the two trees are one meaning (spec_meaning: the order of the Ks given equals the collection's order of its Ks), or one reading is preferred; b300's shaping notes asked the implementer to check exactly this. Blocks release 0.35.2 (.shop/records/2026-11-16-release-0.35.2/plan.md).
Shaped 2026-11-16 (triage: shape; release 0.35.2 blocker, defect batch-40 d1 of b300). Reproduced on a copy of grammar/corpus/constructs/spec: model --root <copy> parse --form 'When the person runs `work start` on a worktree, `work` shall give every file in the worktree, ordered by version, in ascending order to the person.' prints 'refused: more than one meaning: "every file in the worktree, ordered by version, in ascending order" reads 2 ways', tree A t_version_3_k_file_Every (r2_in_Mod k_file_n (the worktree)) Ascending, the order on the every's files, and tree B k_file_Det DetEvery (r2_in_Mod k_file_n (r2_in_By_t_version_3 (the worktree) Ascending)), the order on the worktree inside the modifier 'in the worktree' (0.35.1's reading: ordered(x3 worktree) in the every box's restrictor). The same line with print in place of give is refused the same way on main, so the fault is not only give's: b300 only made it reach a verb whose frame names file. Decision: tree A is kept, tree B is no meaning. Why: the order follows the whole 'every file in the worktree' after its comma; it is the form the unambiguous 'every file that the worktree holds, ordered by version, in ascending order' already gets (every [x5: file] in(x5, x3) scope print(...) ordered(x5, version, ascending)); and an order is a property of what a response acts on (decision 0093), while tree B puts it on a noun phrase inside a restriction that no act acts on, an order of a collection no act takes, which spec_lf_ordered.then (the Then of the act on the collection) was not written for. The two trees are not one meaning in spec_meaning (the atom names a different referent in a different box), so folding them there is not chosen. Fix: r<n>_in_By_<T> is not taken inside a noun's modifier (spec_rgl_np's r<n>_<word>_Mod and the relative clauses take a K2 noun phrase without an order), or, equivalently, spec_lf_ordered.np raises ValueError for an order on a referent made in a modifier so spec_meaning.one drops that tree; the implementer picks the one that leaves the construct catalogue's order-by and order-by-every examples one tree each (model constructs --check). Modules: scripts/spec_rgl_np.py or scripts/spec_lf_ordered.py, grammar/constructs.md regenerated if a signature shows. Scenarios: design-model-check runs model parse on a requirement of the catalogue's context that uses order-by-every on 'every file in the worktree' (of-relation) and checks the exit, beside r317; feature-file-tools runs features generate on such a group and checks its order counter-example as r130 does, which only tree A's form gives. Left out: b301's comma. Depends on nothing.
Rated: high value, high urgency, small, as the triage gave: it blocks release 0.35.2 and a line 0.35.1 parsed is refused; the change is one grammar or form rule and two scenarios beside r317 and r130.
