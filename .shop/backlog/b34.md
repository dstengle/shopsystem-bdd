# A batch-implementer agent type for a batch's tasks

## Notes

The plugin ships no implementer agent, so building-a-batch dispatches each task to a general-purpose subagent with its rules in the brief. A batch-implementer agent (agents/batch-implementer.md) would fix its tools, model and rules (red first, one scenario at a time, never edit a .feature, the Item: trailer, nothing under .shop/backlog/ or .shop/batches/, reply with what it built or one question) in its definition, as pr-reviewer does for the review; building-a-batch step 4 then names it. Raised by the person's question in quote-1, during batch-1.
Shaping (2026-11-06): left shaped, no requirement line. Its subject is an agent definition (agents/batch-implementer.md) and building-a-batch's step 4, which no command runs, so no generated scenario can check it: a line would have an actor (the implementer) whose behaviour only a session shows. Instead: write the agent file and the skill's step by hand as a plain item outside the bar, or carry its fixed parts as a `work decision --tier check` ("a batch's task is dispatched to batch-implementer") enforced by a test that reads agents/batch-implementer.md's frontmatter (tools, model) and building-a-batch's step 4 naming it, with the rules (red first, one scenario at a time, no .feature edits, Item: trailer, nothing under .shop/backlog/ or .shop/batches/, reply with what it built or one question) as `tier: judgement` the pr-reviewer reads. U7 (a worker changes only files in its worktree) is the one line about this subagent and stays as it is.
