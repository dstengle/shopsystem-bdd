# Post to GitHub after the request's commit

## Notes

From batch-1 review 1 (Minor observation): work request, offer, fits, turn, accept, resolve and outcome rewritten post on GitHub before the record's commit; a failed commit leaves an issue or comment with no record, and a re-run of work request opens a second issue. Commit the record first and post after, or make a re-run find the issue it opened.
Shaping (2026-11-06): the record is committed first and GitHub posted after (the review's first suggestion), so a refused commit posts nothing and a re-run of `work request` opens one issue. Lines are written for `work request` (the issue), `work turn` (either side; an all-refused turn also closes the issue) and `work fits` (the asker; it closes the issue); `work offer`, `accept`, `resolve` and `outcome rewritten` post through the same `request_post` path and are to be built the same way, with no line each, since the grammar cannot say "runs a command that posts" (a `posting` command term was tried and dropped). The comment's URL, known only after the post, goes into `## Comments` in a second commit.

## Requirements

### requests

- **uncommittable** (condition of repository): a repository in which git refuses the commit of a request's record, as when a pre-commit hook fails or another process holds the index lock.

#### [g45] `work request` opens no issue when its record is not committed
- [r45] While a repository is uncommittable, if the person runs `work request`, then `work` shall not post an issue.

#### [g46] `work turn` posts nothing when its record is not committed
- [r46] While a repository is uncommittable, if the person runs `work turn` on a request that is `open`, then `work` shall not post a comment or close an issue.

#### [g47] `work fits` posts nothing when its record is not committed
- [r47] While a repository is uncommittable, if the person runs `work fits` on a request that is `awaiting-asker`, then `work` shall not post a comment or close an issue.
