# A request's issue is never left out of step with its record

## Notes

From .shop/batches/9/review-1.md f5 (and the first, refused reply's second observation): after b36, work request leaves an orphaned issue and a record with no issue: when the commit of the issue's URL fails after open_issue succeeded; work fits/resolve leave the record delivered/refused while the issue stays open when gh issue close fails after the URL commit; a failed second commit leaves a posted comment's URL unrecorded. Hardening: close before the second commit, print the posted URL on a failed second commit, or let a re-run find the issue it opened.

Narrowed after batch-9 review 3 (f6, the person's comment on PR #24): f6's fix names a posted comment's or opened issue's URL when the commit of it fails, and a re-run or `work sync` records it without posting again, so the orphaned issue and the unrecorded comment URL are done. Left: `work fits` and `work resolve` leave the record delivered or refused while the issue stays open when `gh issue close` fails.
Merged in from b70 in the 2026-11-16 triage: a failing close in request_post.committed's finally (143-145) replaces the not_recorded refusal: a second case of the close failing.

## Requirements

### context-requests

retired: [r29, r19]
retires: [r53 r29, r54 r19]

#### [g51] A context request is not resolved while its channel rejects a change to its thread
- [r51] While a context request is `accepted` and the context request has a thread on a channel whose availability is `rejecting`, if the person resolves the context request, then the context requests service shall refuse the request and name the thread.

#### [g52] A context request is not served while its channel rejects a change to its thread
- [r52] While a context request is `awaiting-asker` and the context request has a thread on a channel whose availability is `rejecting`, if the person serves the context request, then the context requests service shall refuse the request and name the thread.

#### [g53] A request's issue is never left out of step with its record
- [r53] While a context request is `accepted`, when the person resolves the context request, the context requests service shall set the status of the context request to `delivered`, keep a resolution, set the side of the context request to `asker`, keep an entry on the context request and set the status of the thread of the context request to `closed`.

#### [g54] A request's issue is never left out of step with its record
- [r54] While a context request is `awaiting-asker`, when the person serves the context request, the context requests service shall set the status of the context request to `delivered`, keep a resolution, keep an entry on the context request and set the status of the thread of the context request to `closed`.

### tracking model

```model
object channel
  attributes: availability: available | rejecting
```

- **availability** (attribute) → attribute channel.availability. Whether the channel takes a change to a thread it holds.
- **available** (noun) → value channel.availability available.
- **rejecting** (noun) → value channel.availability rejecting.
