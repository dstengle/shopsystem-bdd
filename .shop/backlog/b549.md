## Requirements

### checking

#### [g95] A port operation that no core line requests is refused
- [r95] While a driven port holds an operation and no core line that uses `response-request` uses the operation, if the person validates this specification, then the specification service shall fail the check and name the operation.

#### [g96] A port outcome that no core line handles and no port line excludes is refused
- [r96] While a driven port holds an operation that has an operation outcome and no core line handles the operation outcome and no port line excludes the operation outcome, if the person validates this specification, then the specification service shall fail the check and name the operation outcome.

#### [g97] A port line relied on by a core line that does not request its operation is refused
- [r97] While a port line that governs an operation supports a requirement id and no core line that has the requirement id uses the operation, if the person validates this specification, then the specification service shall fail the check and name the requirement id.

#### [g98] A port line that no core line relies on is refused
- [r98] While a port line governs an operation and no core line relies on the port line, if the person validates this specification, then the specification service shall fail the check and name the port line.

#### [g99] A port line that excludes an unhandled outcome needs no citation of its core lines
- [r99] While a core line that uses `response-request` uses an operation and a port line that governs the operation supports no requirement id and the port line excludes an operation outcome that no core line handles, when the person validates this specification, the specification service shall complete the request.

### specification model

```model
object driven port kind of area

object port line kind of requirement

object core line kind of requirement

object operation outcome

object operation
  relations: has → operation outcome (many)

object requirement
  relations: handles → operation outcome (many); excludes → operation outcome (many); relies on → requirement (many)
```

- **driven port** (noun) → object driven port. An area whose kind is `port`: the operations and words by which the core reaches one upstream bounded context, in this bounded context's own words (decision 0122). Plural: driven ports.
- **port line** (noun) → object port line. A requirement of a capability that a driven port holds: what the core needs of the upstream that the port reaches. Plural: port lines.
- **core line** (noun) → object core line. A requirement of a capability that no driven port holds. Plural: core lines.
- **operation outcome** (noun) → object operation outcome. One outcome that an operation of the domain model declares: `done`, `returned`, `passed`, `failed`, or `refused` with one of its reasons. Plural: operation outcomes.
- **handle** (verb, state) → relation requirement.handles. A requirement's trigger is an operation outcome of a request the core makes: a When line on an outcome, an If line on a refusal (decision 0127). Forms: handles, handled. Frame: <requirement> handles <operation outcome>.
- **exclude** (verb, state) → relation requirement.excludes. A port line says that the upstream does not give an operation outcome, as a port line whose response says "shall not refuse the request" excludes the refusal. Forms: excludes, excluded. Frame: <requirement> excludes <operation outcome>.
- **rely on** (verb, state) → relation requirement.relies on. A core line stands on a port line: the core line requests the port line's operation and the port line excludes an operation outcome that no core line handles, or the port line names the core line under its `Relied on by:` (decision 0126). Forms: relies on, relied on. Frame: <requirement> relies on <requirement>.
