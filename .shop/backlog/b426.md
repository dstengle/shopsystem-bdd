# A core driver runs the generated scenarios against the service's operations in process, not through a port adapter

## Notes

Raised 2026-11-20 while designing b418: the domain contract design's §6.2 drives the scenarios through a protocol driver, and the only one is driver_cli (cli.toml to argv, the command run with --json). The person: create is an operation of the core model, not of the port; adapters depend on the core and the scenarios test the core's business logic. A core driver calls each operation by its model name in process and gives back the same Response envelope; the handlers keyed on WhenRequests <service>.<operation> call it; the Givens build state through the core's own operations, never by reading a collection out of the store. The CLI adapter is tested apart: v_a1-v_a4's conformance of cli.toml to the model and the program's argparse, and a thin adapter test. A consumer app then needs a core entry point that the scaffold (migrate init) and getting-started give it. Neither the Gherkin nor the grammar changes; the domain contract design's §6.2 does (a design-decision).
