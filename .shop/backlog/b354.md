# the spec model commands: write a domain model area, a vocabulary entry and an operation by command

## Notes

The domain contract (design §4.5, §11): spec/model/<area>.md is written by hand on the branch; a command (spec model ...) writes its elements, as work line writes an item's lines. Raised by phase 4 for model forms.
UX trial 2026-11-19 (a checklists CLI bootstrapped from an empty repository at 0.39.0): a fresh context's first model area and vocabulary layers (spec/model/checklists.md, spec/vocabulary/checklists.md and shared.md with its actor) had to be hand-written by copying docs/examples/notes-cli/; `spec forms --check` exited 0 with them, and main's `spec check` stayed red (v_m4, v_m7, w_m5) until a batch laid the lines that use them. See also b387 (the item's new capability refuses --model and --term).
Scoped 2026-11-20 to what a new user needs: a term (vocabulary entry) written into an item that holds a capability new to the context is kept in the item, in the new capability's area (`work line --into <capability> --term`); a model element is b387's model line, so together they give a fresh context's first item its model and vocabulary by command, laid by its batch, with no hand-written spec/model/ or spec/vocabulary/. Writing an area, an entry or an operation straight into spec/ outside an item, and spec/vocabulary/shared.md, are cut into b398. directive-10 onboarding.

## Requirements

### drafting

#### [g25] A term written for a new capability of an item is kept
- [r25] While an item holds a capability that does not exist, when the person writes a term into the item, the drafting service shall keep the term in the item.

### tracking model

```model
service drafting
  operation write(term, item)  outcomes: done
```

- **write** (verb, action) → operation drafting.write. Forms: writes, wrote, written. Frame: <actor> writes <term> into <item>.
