# A lay regenerates the features and corpus blocks its model changes reach

## Notes

batch-121: b666's model change altered features/product.feature and the corpus blocks of product r18 and r20, but work batch start regenerates only the laid capabilities, so done and review failed until the task regenerated them by hand.
Shaped from the idea's note (batch-121, b666): a lay regenerates the feature and the corpus block of each capability its model lines reach, not only the laid capabilities. One line in batches: an item's model line specifies an operation a requirement of a capability the item holds no line of governs; opening the batch generates that capability's feature and keeps the requirement's logical form in the corpus. Technical call: batch_start regenerates, after laying the model lines, every service capability's feature and every corpus block whose text features generate or spec parse --form now writes differently (not only the governing ones the line checks); governs is the world the scenario builds. World that fails first: the item's model line restates an operation (a parameter added) that a requirement of another capability requests with that parameter's value written into its feature's step, and its corpus block holds the form before; today start lays the model line and leaves that feature and block as they were.
