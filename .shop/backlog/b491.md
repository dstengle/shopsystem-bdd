# work batch review merges task branches that conflict in task order, each into the next, and refuses only a real conflict

## Notes

work batch review (batch_merge.merge) merges each in-batch item's branch into batch-<n> in plan order and refuses any conflict but the unbuilt: line with git's first CONFLICT line and the branch only, so batch-51's conflicts were settled by hand on a later branch (b387 merged b354; b391 merged b387). The submit request is to merge the task branches in task order, each after the ones before (git's rerere reusing a settled resolution, else a three-way merge), and refuse only a conflict that remains, naming the file and both items. A conflict is stated as a state relation of kept changes; submit declares the refusal reason. From the missing-command research, the person's words in quote-68.
Rated medium-value (batch-51 and later batches had task-branch conflicts settled by hand on a later branch; a refusal naming the file and both items tells the driver what to settle), medium-urgency (every batch of seven items risks a stop at review), medium (batch_merge.merge in task order with rerere, the refusal's names, the submit reason in the model and the scenario handlers of two conflicting branches).

## Requirements

### reviews

#### [g7] A batch whose task branches touch one file without a conflict is submitted, merged in task order
- [r7] While a batch is `building` and every task of the batch is `done` and an item in the batch is `in-batch` and a kept change that touches a file cites the item and another kept change touches the file and another item in the batch is `in-batch` and the kept change cites the item and no kept change conflicts with a kept change, when the person submits the batch, the batches service shall keep a proposed change of the batch that holds the kept change and set the status of the batch to `in-review`.

#### [g8] A batch whose task branches conflict is not submitted, naming the file and both items
- [r8] While an item in a batch is `in-batch` and a kept change cites the item and another item in the batch is `in-batch` and the kept change conflicts with another kept change that cites the item and the kept change touches a file, if the person submits the batch, then the batches service shall refuse the request and name the file, the item and every item in the batch that a kept change that conflicts with the kept change cites.

### execution model

```model
object kept change
  relations: conflicts with → kept change (many)

service batches
  operation submit(batch)  outcomes: done → the proposed change | refused: task not done, kept change citing no item, file conflicting
```

- **conflict** (verb, state) → relation kept change.conflicts with. A task's kept change alters a part of a file that a kept change of an earlier task in the batch alters otherwise, so that merging the task branches in task order, each after the ones before, with git's recorded resolutions, leaves the part unsettled; the `unbuilt:` line of a capability never conflicts. Forms: conflicts, conflicted. Frame: <kept change> conflicts with <kept change>.
- **conflict** (verb, state) → relation kept change.conflicts with. A task's kept change alters a part of a file, other than a capability's `unbuilt:` line, that a kept change of an earlier task in the batch alters otherwise, so that merging the task branches in task order, each after the ones before, with git's recorded resolutions, leaves the part unsettled. Forms: conflicts, conflicted. Frame: <kept change> conflicts with <kept change>.
