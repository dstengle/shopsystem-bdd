# A port adapter's design artifact: how it fulfils its port's lines and maps them onto upstream contracts

## Notes

The person, 2026-11-24 (quote-72): a design artifact or artifacts for a port adapter, including how requirements are implemented and how they map to upstream services. The port's lines set the requirements and generate the scenarios; the adapter's design does not fit in the core; for an internal upstream with a full contract the mapping tells the context when to request a capability addition or change. Evidence: the two worked examples of 2026-11-23 (ordering over inventory and payments; port contracts and swapped providers).
This item is C-5 of the contracts design: the adapter spec kind, a nested context id, realises: and providers: read, adr/ and provider/ accepted, the port read from the parent at its commit (decisions 0123, 0117).
Shaped 2026-11-25 (decisions 0123, 0124, 0117): the adapter spec's structure as four checking lines of the specification service validating an adapter spec: its adapter decisions and its providers' contracts accepted, its id in the adapter spec id form, each realised requirement id a line that exists, each provider's contract held. An adapter spec stays nested in its bounded context's spec, no hosted bounded context of the shop and no area of the parent's model. Technical call: reading the parent's driven port at the parent's revision is left to the implementation and an adapter decision, no line names it (mechanisms in ADRs); the realises check is C-7's. Rated high value (the person's quote-72, C-5 of the contracts design), medium urgency, medium size.
Wording after decisions 0129 and 0133: an adapter spec is nested in its bounded context's spec (decision 0123), not a bounded context a shop hosts; its id is the parent's id with /adapter/<name>, the parent's id flat under the product.

## Requirements

### checking

#### [g73] An adapter spec with its adapter decisions and its providers' contracts is valid
- [r73] While an adapter spec holds an adapter decision and the adapter spec holds a contract of a provider of the adapter spec, when the person validates the adapter spec, the specification service shall complete the request.

#### [g74] An adapter spec whose id is out of the adapter spec id form is refused
- [r74] While the id of an adapter spec does not conform to the adapter spec id form, if the person validates the adapter spec, then the specification service shall fail the check and name the id.

#### [g75] An adapter spec that realises a line that does not exist is refused
- [r75] While an adapter spec realises a requirement id that no requirement has, if the person validates the adapter spec, then the specification service shall fail the check and name the requirement id.

#### [g76] An adapter spec that holds no contract of its provider is refused
- [r76] While a provider of an adapter spec has no contract that the adapter spec holds, if the person validates the adapter spec, then the specification service shall fail the check and name the provider.

### specification model

```model
object adapter spec kind of specification
  relations: has → id (one); realises → requirement id (many); has → provider (many); holds → adapter decision | contract (many)

object provider kind of bounded context
  relations: has → contract (many)

object adapter decision kind of design-decision

object adapter spec id form kind of artifact
```

- **adapter spec** (noun) → object adapter spec. The specification of one adapter of a driven port, kept nested in its bounded context's spec, with its own index of kind adapter, its realisation lines, its providers' contracts and its adapter decisions, read with its parent's driven port and neither an area of the parent's domain model nor a bounded context of its own (decision 0123). Plural: adapter specs.
- **provider** (noun) → object provider. A bounded context whose operations an adapter spec requests, named under the adapter spec's `providers:`. Plural: providers.
- **adapter decision** (noun) → object adapter decision. A design-decision of an adapter spec on a mechanism it uses, such as a transport, a retry, a store, a timer or polling (decision 0124). Plural: adapter decisions.
- **realise** (verb, state) → relation adapter spec.realises. An adapter spec names under its `realises:` the requirement id of a line of its parent's driven port that it fulfils. Forms: realises, realised. Frame: <adapter spec> realises <requirement id>.
- **the adapter spec id form** (proper noun) → object adapter spec id form. The id of an adapter spec: the id of its parent bounded context followed by `/adapter/<name>` (decision 0123).
