# The product commands take one bounded-context id form

## Notes

New-user trial of 2026-11-26 (quote-103): migrate init and work context use bounded-context/example.org/...; spec context, assign and plays examples use unprefixed ids; both were accepted as two contexts in product.toml ([contexts."example.org/chores/chores-app"] and [contexts."bounded-context/example.org/chores/chores-app"]) with one job each, and spec check read both as this context.
The product commands take the bounded-context id in the one form migrate init and work context use, bounded-context/<domain>/<path> (the context id form); declaring a bounded context, assigning a job to one and mapping a product actor in one with an id of another form are refused naming the id, so one id never makes two contexts. The trial's evidence in quote-103; the person's words in quote-104.
Rated high value and high urgency: an id in the other form silently made a second bounded context in the trial and spec check read both as this context, and b792's docs rest on one form; small: one refusal reason on three operations and its check of the context id form, which contract_obtain already has.
Its restated assign/map model lines take the union of the refusal reasons b793, b794 and b798 add, so the three lay in any order.

## Requirements

### product

#### [g37] A bounded context whose id is out of the context id form is not declared
- [r37] If the person declares a bounded context with an id that does not conform to the context id form, then the product service shall refuse the request and name the id.

#### [g38] A job is not assigned to a bounded context whose id is out of the context id form
- [r38] If the person assigns a job to a bounded context whose id does not conform to the context id form, then the product service shall refuse the request and name the id.

#### [g39] A job assigned to a bounded context the product does not hold is refused
- [r39] If the person assigns a job to a bounded context that is not in the product, then the product service shall refuse the request and name the bounded context.

### specification model

```model
service product
  operation declare context(bounded context, id, subdomain, shop)  outcomes: done → the bounded context | refused: id outside the product, subdomain outside the product, id not in the context id form
  operation assign(job, bounded context)  outcomes: done → the job | refused: job assigned already, id not in the context id form, bounded context outside the product
```
