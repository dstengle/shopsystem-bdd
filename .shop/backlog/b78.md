# work watch wakes on GitHub's events, not a 60-second poll

## Notes

The person wants the request watch event-driven through Claude Code's Monitor tool rather than polling every 60 seconds, the person's words in quote-6, and put at the top of the queue for next work in quote-7. `work watch --forward` takes GitHub's events: on each GitHub repository whose issues it watches and that the account administers, it runs `gh webhook forward` (the cli/gh-webhook extension, installed if missing) for the issues and issue_comment events to a listener on a local port, and prints a comment the request does not hold, or an untaken ask, as its event arrives, then exits as `work watch` does (r43, r44). On a repository the account does not administer (an upstream's, when this context is the asker), or when gh cannot forward, it falls back to polling the notifications API (GET /notifications with If-Modified-Since, at its X-Poll-Interval, 60 s here; a 304 costs no rate limit), and says on stderr which repositories it polls. The skills raising-a-request, taking-in-a-request and building-a-batch start it with the Monitor tool (command `work watch --forward`, timeout at the maximum, re-armed on each expiry and after each work sync), in place of Bash run_in_background. Researched 2026-11-06: webhooks are GitHub's only push for issues and need admin rights on the repository; the notifications API is polling, but cheap.
