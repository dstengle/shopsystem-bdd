# work's push never hangs on a slow or prompting remote

## Notes

From .shop/batches/7/review-1.md (observation 1): shop_files' push (scripts/shop_files.py, push_failure) passes no timeout and no GIT_SSH_COMMAND with -o BatchMode=yes, so an SSH remote asking for a passphrase or host key, or a remote that does not answer, hangs every committing work command, and a batch command while it holds the batch lock. Add BatchMode=yes and a timeout; a push that times out is reported like a refused one.

Rated: value medium-value: a hang stops every committing `work`, `measure` and `migrate` command, and a batch command while it holds the batch lock, though this repository's remote is HTTPS with gh's credential helper, where it has not happened yet. Urgency medium-urgency: since b51 every commit pushes, so any SSH or unreachable remote now hangs every command. Size small: one function in scripts/shop_files.py and one scenario's handlers.

How (for the task, not a line): the push runs with `GIT_SSH_COMMAND` holding `-o BatchMode=yes` (kept over a `GIT_SSH_COMMAND` already set, by appending the option), and a timeout in seconds, read from `$SHOPSYSTEM_PUSH_TIMEOUT` (default 60), so the scenario sets it to 1 or 2. A push past the timeout is printed like a refused one: `not pushed: <remote>: timed out after <n> s`, the commit kept, exit 0. Kill the whole process group on the timeout (`start_new_session=True`, `os.killpg`): `subprocess.run(..., timeout=)` kills only git and then waits for the pipes that git's children (receive-pack, a hook) still hold open, which hangs again. The silent remote in the scenario is a bare repository whose pre-receive hook sleeps a bounded time (e.g. `sleep 30`), never forever, so the scenario ends even before the timeout is built; U4 is not asked under it, as under an unpushable remote (`_shop_unpushable` in tests/scenarios/backlog_handlers_remote.py). The prompting SSH remote is not a scenario (BatchMode only acts on a real ssh); the timeout is its backstop.
