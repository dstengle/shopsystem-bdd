# A bounded context asks another for its context: its glossary, capabilities and lines, without a request for new behaviour

## Notes

The person, 2026-11-17 (quote-49): 'We also need to provide a way for a BC to request the context from another BC.' Today a context sees an upstream's lines only through work offer on a request (r73, r112-r115: a capability's lines and the terms they mention, quoted on the request's issue), so it must first ask for behaviour. Wanted: a downstream (or the product) asks an upstream for its context (glossary, capabilities, requirement lines) as its own exchange, and gets it in a form it can read; it is what b42's term negotiation and a request's lines stand on. Related: b42, b13, b40.
This item is C-2 of the contracts design: obtaining writes provider/<upstream>/<version>/ of an adapter spec (decision 0117); the published contract's form is its own item.
b547 (ready) declares object contract kind of artifact in the specification area with its term contract and the contract form; when this item is shaped again its contract entry and object header are to build on those, not repeat them (v_t20).

## Requirements

### specification model

- **obtain** (verb, action) → operation contracts.obtain. Forms: obtains, obtained. Frame: <actor> obtains <contract> from <bounded context>.
- **the contracts service** (proper noun) → service contracts.
- **downstream context** (noun) → object downstream context. A bounded context that builds on the contract of this bounded context. Plural: downstream contexts.
- **status** (attribute) → attribute contract.status. Where a contract stands: `published` while it is the latest, `superseded` once a later one is published.
