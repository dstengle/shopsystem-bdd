# A bounded context publishes its contract at a version and a downstream context fetches it without a context request

## Notes

The person, 2026-11-17 (quote-49): 'We also need to provide a way for a BC to request the context from another BC.' Today a context sees an upstream's lines only through work offer on a request (r73, r112-r115: a capability's lines and the terms they mention, quoted on the request's issue), so it must first ask for behaviour. Wanted: a downstream (or the product) asks an upstream for its context (glossary, capabilities, requirement lines) as its own exchange, and gets it in a form it can read; it is what b42's term negotiation and a request's lines stand on. ## Requirements

### checking

#### [g73] A contract published keeps the specification at a version
- [r73] When the person publishes a contract with the `1.2.0` version, the specification service shall keep a contract that has the `1.2.0` version.

#### [g74] A later contract supersedes every published one
- [r74] When the person publishes a contract with the `1.3.0` version, the specification service shall set the status of every contract whose status is `published` to `superseded`.

#### [g75] A contract at a version already published is refused
- [r75] While a contract has the `1.2.0` version, if the person publishes a contract with the `1.2.0` version, then the specification service shall refuse the request and name the version.

#### [g76] A contract is refused while a requirement is out of the language
- [r76] While a requirement does not conform to the language reference, if the person publishes a contract, then the specification service shall refuse the request and name the requirement.

#### [g77] A contract published holds the requirements and the terms
- [r77] When the person publishes a contract, the specification service shall keep a contract whose status is `published` and keep every requirement and every term in the contract.

#### [g78] A downstream context fetches the published contract without a context request
- [r78] When a downstream context fetches a contract, the specification service shall return the contract whose status is `published` and change nothing.

#### [g79] A contract fetched at a version never published is refused
- [r79] While no contract has the `2.0.0` version, if a downstream context fetches a contract with the `2.0.0` version, then the specification service shall refuse the request and name the version.

#### [g80] A downstream context fetches a contract at a version
- [r80] When a downstream context fetches a contract with the `1.2.0` version, the specification service shall return the contract that has the `1.2.0` version.

### specification model

```model
object contract
  attributes: status: published | superseded
  lifecycle status: published → superseded
  relations: has → version (one); holds → term | design-decision (many)

object downstream context kind of agent

service specification
  operation publish(contract, version) by the person
    outcomes: done → the contract | refused: version already published, requirement not in the language
  operation fetch(contract, version) by downstream context
    outcomes: returned → the contract | refused: version not published

event contract published: raised by specification.publish
```

- **published** (adjective) → value contract.status published.
- **superseded** (adjective) → value contract.status superseded.
- **status** (attribute) → attribute contract.status. Where a contract stands: `published` while it is the latest one of its bounded context, `superseded` once a later one is published.
- **publish** (verb, action) → operation specification.publish. Forms: publishes, published. Frame: <actor> publishes <contract>.
- **fetch** (verb, action) → operation specification.fetch. Forms: fetches, fetched. Frame: <actor> fetches <contract>.
- **downstream context** (noun) → object downstream context. A bounded context that builds on the contract of this bounded context and reaches it through a driven port of its own. Plural: downstream contexts.
