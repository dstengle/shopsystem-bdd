# The adapter unlay restores operation tables against the batch's base, never removing or restoring the wrong one

## Notes

The person's words in quote-68. Defect in scripts/backlog_adapter.py unlay (lines 189-209): it restores each operation the item's adapter block names to the newest version git holds of the contract whose state of that operation differs from now, not to the batch's base. Reproduced in a scratch repo: the contract held notes.add as 'notes add old', then 'notes add' (the base); an item exposing the same 'notes add' table is laid (the laid state equals the base), and unlay brings back 'notes add old', a table from before the base. The same walk takes a wrong version when a later commit on the branch (another item's table for the same operation, a task's tree in batch_parked.tested_tree) changed the operation, and removes the table outright where git holds no version (versions == []). Callers: batch_start.unlay_lines from batch_parked.take_out (line 42), batch_parked.tested_tree (line 74) and batch_review (line 100) via backlog_lines.unlay (line 240). Fix: unlay takes the base the batch was laid on (the base commit as_laid already reads, the commit that added the plan, or the batch branch's fork point) and puts each named operation's table and its [unexposed] entry back as the contract at that commit held them, no table and not unexposed when it held none; nothing else in the contract changes. A chore, not a line: a defect inside the existing behaviour of batches#r60 (park takes the item's lines out of the batch's workspace) that a script test shows; saying 'as the base held it' needs a word for the batch's base the vocabulary lacks.
