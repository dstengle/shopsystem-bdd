# Resolve the delivered item's request at the merge

## Notes

from batches' Not yet; see .shop/records/2026-11-05-backlog-inventory.md row 6
Today `work batch merged` sets each in-batch item delivered, but the request an item was taken in from (`work accept`'s `request:` field) stays `accepted` until someone runs `work resolve` by hand, which batches' `## Not yet` names (inventory 2026-11-05 row 6; triage 2026-11-16, requests cluster on top of b26; no person's decision, no quote). Change: batch_close.py's merged, for each delivered item with a `request`, calls request_moves.resolve on that request when it is `accepted`, with each accepted line's requirement id (its id on the item after batch start's renumbering) and as its version the batch's merge commit; a request not `accepted` is left alone and named in what merged prints. For the line-to-id map, request_accept.py records on the item which request line each of its lines came from, and backlog_lines.renumber carries it. The scenario: an item taken in from an accepted request, in a batch whose pull request gh says is merged; `work batch merged` leaves the request `delivered` in the asker's turn, with a resolution, a resolve comment on its issue and the issue closed. Left out: a request whose lines were spread over several items (resolved when the last of them is delivered: a later item); reworded lines are still resolved by their recorded request line. The batch also drops the matching bullet from batches.md's `## Not yet` and adds batch_close.py's new concern to its module-map row. A post that fails at the merge leaves the item delivered and the request as request_post leaves it (the record put back), named in the output for a later `work resolve`. Depends on nothing (b26 delivered). Rating kept from the inventory: value medium (a request stays open after its work ships, and the asker is not told), urgency medium, size small (one call from batch_close plus the line map).
