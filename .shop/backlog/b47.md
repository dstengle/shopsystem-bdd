# A parked item's lines leave the other tasks' worktrees

## Notes

Found in batch-3: b45 was parked because its generated scenario could not run (a step with no words, see b46), but its lines and feature stayed on batch-3 and so on t2's branch, so `work batch done batch-3 t2` failed the suite on b45's scenario. `review` takes a parked item's lines out only once every task is done, so the batch could not go on; it was abandoned and b43 restarted as batch-4. `park` should take the parked item's lines out of batch-<n> (unlay_lines) at once, and `done` run a task's tests with them out (merging batch-<n> into the task branch, or testing against it).
Shaping (2026-11-06): two lines in batches. r14: a park removes the parked item's requirements (from batch-<n>, at once, as `unlay_lines` does at review). r15: with a parked item's scenario not passing, `work batch done` on another running task still sets it done; how (merging batch-<n> into the task branch before its tests, or testing against batch-<n> with the task's commits) is the implementer's choice. It adds the relation row `| scenario | of | item | |` to batches.
renumbered by work batch start: batches#g14 -> batches#g17, batches#r14 -> batches#r17, batches#g15 -> batches#g18, batches#r15 -> batches#r18

#### [g17] A park takes the parked item's lines out of the batch
- [r17] While an item that is `in-batch` proposes a requirement, when a batch parks the item, `work` shall remove the requirement.

#### [g18] A parked item's failing scenario does not hold up another task
- [r18] While an item in a batch is `needs-input` and a scenario of the item is not passing, when a session runs `work batch done` on a task of the batch that is `running`, `work` shall set the status of the task to `done`.
