# An obtained contract is kept where its adapter spec reads it, and spec obtain's edge cases

## Notes

batch-91: spec obtain keeps an upstream's contract at provider/<upstream>/<version>/ at the repository root, a stopgap until adapter specs exist (b540); keep it under the context's spec where the adapter spec's provider reads it. Review 1's observations: a malformed bounded context id refused with the wrong reason; a missing or private repository reported as having no contract; two upstreams whose ids end in the same word share one folder (key it by the whole id); a CRLF contract not kept byte for byte.
Relates to b540: b540's adapter spec holds a contract of each provider (checking r83, r86); where an obtained contract is kept should be where b540's adapter spec reads it. A provider is a kind of bounded context and uses b587's bounded context has → contract.
spec obtain (b587) keeps a contract at provider/<upstream>/<version>/ at the repository root, keyed by the id's last word; decision 0117 and b540 (building in batch-93) put it in the adapter spec of the provider. Lines: the four edge cases of batch-91's review (a malformed id refused for its own reason, an unreachable bounded context not reported as having no contract, two bounded contexts whose ids end alike each keeping its own contract, a contract kept byte for byte) and, once b540 is merged, the line that the obtained contract is held by the adapter spec of its provider (needs b540's words adapter spec and provider).
Rated medium value (obtain's refusals told apart and contracts never overwritten, a downstream's footing), medium urgency, small. The CRLF case is a defect of b587's r81, split out as its own chore item.

## Requirements

### checking

#### [g84] A contract is not obtained by an id out of the context id form
- [r84] If the person obtains a contract from a bounded context whose id does not conform to the context id form, then the specification service shall refuse the request and name the id and the `id not in the context id form` reason.

#### [g85] A bounded context that cannot be reached is not reported as having no contract
- [r85] If the person obtains a contract from a bounded context whose availability is `unreachable`, then the specification service shall refuse the request and name the bounded context and the `bounded context unreachable` reason.

#### [g86] A contract obtained keeps every other bounded context's contract as it was
- [r86] When the person obtains a contract from a bounded context, the specification service shall keep the contract and change no contract of another bounded context.

### specification model

```model
object bounded context
  relations: has → id (one)
  attributes: availability: available | unreachable

service specification
  operation obtain(contract, bounded context, version) by the person
    outcomes: done → the contract | refused: bounded context with no contract, id not in the context id form, bounded context unreachable

object context id form kind of artifact
```

- **the context id form** (proper noun) → object context id form. `bounded-context/<domain>/<path>`, the whole id a bounded context is obtained from and its contract kept under.
- **availability** (attribute) → attribute bounded context.availability. Whether the specification service reaches a bounded context to obtain its contract.
- **available** (adjective) → value bounded context.availability available.
- **unreachable** (adjective) → value bounded context.availability unreachable.
