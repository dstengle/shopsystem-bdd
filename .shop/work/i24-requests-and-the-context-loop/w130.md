# work start makes the initiative of an accepted request; an initiative done when its work is green and its requests delivered

## Questions
- Does `work run` count as 'a `work` command' under work-queue#r23, so that its move of an initiative's last work-item to green sets the initiative to done? Reading A, yes: after `work run i1` takes i1's last work-item to green (and no request this context asked naming i1 is undelivered), .shop/work/i1/initiative.md gives status done, committed with the work-item. The accepted supervision scenarios at features/supervision.feature:142-148 ('.shop/work/i1/initiative.md is as it was') and :159-164 ('as that session committed them') then fail and must be re-formulated before this work-item can go green. Reading B, no: only `work withdraw`, `work retry` and `work answer` set done. After `work run` greens the last work-item, initiative.md stays started, and no later command makes the condition true, because it already holds. The narrator would see such an initiative never become done unless its last change is a withdraw, retry or answer. No supervision test breaks.
- Important, scripts/workqueue.py:195-208: work retry returns a work-item to green (log green->failed after work run's push failure, supervise_faults.py:78-85) without running the r23 done check, so the initiative stays started; add the withdraw hook (workqueue_done.becomes/mark, initiative.md in the commit) to retry.

## Answers
- 2026-10-24: Reading B (the coordinator, under the person's delegation): work run is not one of the work commands r23 means; only work withdraw, work retry and work answer (and the request commands, when they make the condition true) set the initiative to done, and the supervision scenarios stand. That an initiative whose last work-item work run greens stays started is a known gap, recorded as an observation for a later line.
