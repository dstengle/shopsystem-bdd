## Questions
- work-queue#r39: how does `work list` in this context know that a request an initiative raised into an upstream is not yet `delivered`? Requests are kept only in the upstream's repository (requests Implementation, decision 0067), and this context keeps no record of one it raised. Reading A: this context keeps its own record of each request it raised (which upstream, the request's id there, the initiative it was raised for, and its last known status). `work list` reads only that record. The narrator sees i1 as waiting on q1 until that record is updated, even after the upstream delivers, and `work list` never fails because the upstream cannot be reached. Reading B: `work list` reads each raised request where it is kept, in the upstream's repository, through a registered location of the upstream. The narrator sees the upstream's current status, so the waiting line goes as soon as the upstream delivers. But `work list` depends on reaching the upstream and exits with an error, or prints the status as unknown, when it cannot. Reading C: a request raised into an upstream is also kept in this context's .shop/work/requests/, with its asker as this context, its upstream named and `part_of`/`source` naming the initiative, as work-queue r23 reads requests. `work list` reads that copy. The narrator sees what reading A gives, and the copy's status follows the upstream only when `work` writes it there.

## Answers
- 2026-10-27: Reading A: this context keeps its own record of each request it raised (the upstream, the request's id there, the initiative it was raised for, its last known status), and work list reads only that record; it never fails because the upstream cannot be reached. Chosen as the one a test can check without the upstream, matching q14 line 4 (the asker acts from its own repository, with no checkout of the upstream's) and decision 0067 (requests kept only in the upstream's repository), which reading C would contradict (answered by the coordinator under the person's delegation of 2026-10-27).
