## Questions

2. requests r3 for an internal request: (a) as drafted, narrowed to "a request whose asker is the upstream itself"; (b) an internal request may also be raised with `--raised-for` alone: "[r3] **If** a request whose asker is the upstream itself is raised with none of `--source`, `--thread` and `--raised-for`, **then** `work request` shall refuse, because the request names neither an origin, a job-thread nor a request it is raised for, and change nothing."
3. requests: how `work request`, run in the asker's own repository (line 4), names the upstream it raises into. The note does not say. If an option: "[r44] **When** `work request` is run with `--to <upstream>`, `work` shall raise the request into that upstream's carrier."
4. requests, glossary: "message" (lines 18, 20, 22) and "take in" (lines 1, 14, 18, 19) are neither terms nor spelled out. Entries if yes: "- **message**: what one side of a request sends the other through its carrier: a line outcome, a question, an answer or the turn." and "- **take-in**: the upstream's reading into its own repository of every request and message its carriers hold."
5. requests r43, line 22's "the contract's form": (a) as drafted, the form `work request` writes ("the fields of a request's form"); (b) a contract shared between contexts, which then needs a term and an entry.
6. requests r35-r38 (lines 13-16), "show": (a) the response of `work show` run in that side's repository, e.g. "[r35] **When** `work show` is run in the asker's repository while a request is in the asker's turn, `work` shall print that it is the asker's turn, with each question the asker has not answered."; (b) of `work status`; (c) as drafted, with no command named.
7. requests r41 (line 20 with answer 1): the note does not say where the upstream's allow list is kept or how an asker id is allowed. If a command: "[r45] **When** `work allow <asker> <asker id>` is run in the upstream's repository, `work` shall allow requests and messages from that asker id for that asker."; if a setting, Implementation only.
8. supervision r135 (line 24) when the fulfilled request gives no delegation: (a) "[r137] **Where** the request an initiative fulfils gives no delegation, **when** a round of the kind `integrate` gives the lines of a request into an upstream, `work run` shall raise them with no delegation."; (b) "... `work run` shall raise nothing and write a question for the person under the initiative's ledger."
