# batch-178 review 1

## Verdict

The batch builds b874's lines: each item is applied alone in its task's workspace at opening, validated there, reopened when it fails and committed citing the item. Amend applies only on the task. Submit rebuilds the specification from the base. All runs exit 0. One finding to fix: at submit, the rebuild and the merge throw away whatever a task changed by hand under `spec/`, `features/`, the corpus or the catalogues, and give no sign of it. The change is also over the size limit.

## Findings

### f1 Important fix now: submit silently discards a task's own changes under spec/, features/, the corpus and the catalogues
- item: b874
- where: scripts/batch_merge.py:61
`batch_rebuild.taken` (scripts/batch_rebuild.py:34) and `batch_merge._ours` (scripts/batch_merge.py:61) take every path under `OWNED` from the rebuild's commit. `OWNED` is the whole of `spec/` and `features/`, plus `grammar/corpus/spec/`, `grammar/rules.md` and `grammar/constructs.md`. `_ours` also `git rm`s any such file that only the task branch added. The only part of a task's work in those paths that survives is the ids `built_on` takes out of `unbuilt:`. So at submit the batch silently loses all of these:

- a corpus block the task corrected. The batch brief tells tasks to do exactly this (scripts/batch_driver.py:173: "the task whose item changes the grammar reads it against the line and corrects it").
- a design-decision or an Implementation-section edit the task wrote under `spec/`. 27 capability files have an Implementation section.
- a catalogue row for a new rule code the task's code adds.
- features regenerated by a generator the task changed. `rebuilt` applies the items in a worktree of `batch.forked_from`, so `batch_generator` writes the features with the base's `scripts/features`, not the batch's. The kept `features/` then disagree with the batch's generator, and `features generate --check` fails after submit.

Nothing refuses or names the discarded paths. The test (tests/scripts/test_batch_merge.py:14) asserts the discard as the intended behaviour. No line asks for a task's work to be dropped: reviews#r20 asks to apply the item to the batch's specification, not to replace what the task built. This batch's own submit escaped only because it ran the review code from `main`.

Fix: after the rebuild, keep each owned path the task branch changed since its `lines_commit`, other than the apply's own outputs. Run the rebuild's generator, corpus and catalogue writes with the batch's tree, i.e. the merged code. At least refuse the submit and name each owned path a task changed that the rebuild would overwrite.

### f2 Minor observation: an amend of a dependent item drops the lines of a blocker that is not on its start branch
- item: b874
- where: scripts/batch_amend.py:110
Some dependents have more than one picked dependency. At opening, `batch_applied.applied` starts such a dependent's worktree from the last one's task branch, and applies the others (`before`) in the dependent's own apply commit. An amend puts the apply's paths back to `lines_commit^`, the start branch's head, which does not hold the `before` items. It then applies only `[item]`. After the amend, the dependent's workspace no longer holds those blockers' lines, which r202 makes it hold at opening.

Reproduction: pick b1 and b2 independent, and b3 depending on both. Open the batch, then run `work batch amend b3`. The task branch of b3 now lacks b1's requirement.

b889 owns amending with dependents, so this is recorded and does not hold the merge.
